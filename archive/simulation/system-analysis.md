# Системный анализ: Какой должна быть система A2A

## Что показала симуляция

Симуляция показала **паттерн взаимодействия**:
1. Клиент и сервер обмениваются сообщениями
2. Каждое сообщение содержит контекст и инструкции
3. Процесс итеративный — один запрос не решает задачу

## Из чего состоит система

### 1. Слой транспорта (как передаём)

**Вопрос:** Как клиент и сервер общаются?

**Варианты:**
- HTTP REST API (текущий)
- WebSocket (для real-time)
- CLI → Server (для локальных клиентов)

**Что нужно:** Единый формат сообщений независимо от транспорта.

### 2. Слой протокола (что передаём)

**Вопрос:** Какую структуру имеют сообщения?

**Элементы протокола:**
- `new_task` — задача от пользователя
- `context` — накопленное состояние
- `codeBlocks` — фрагменты кода
- `questions` — вопросы сервера
- `instructions` — инструкции клиенту
- `outcome` — статус (продолжить/завершить)

**Что нужно:** Спецификация протокола.

### 3. Слой логики сервера (как анализируем)

**Вопрос:** Что сервер делает с полученным?

**Компоненты:**
- Классификатор задач (mechanical/semantic)
- Граф знаний (entities, relations)
- Нейроны (детекция паттернов)
- Генератор инструкций

**Что нужно:** Понять, как нейроны связаны с задачами.

### 4. Слой логики клиента (как действуем)

**Вопрос:** Что клиент делает с инструкциями?

**Компоненты:**
- Сборщик контекста (package.json, composer.json)
- Сканирователь файлов
- RAG индексатор
- Применитель изменений
- Интерфейс для вопросов

**Что нужно:** Понять, что клиент МОЖЕТ делать.

### 5. Слой хранения (где состояние)

**Вопрос:** Где хранится контекст между итерациями?

**Варианты:**
- На сервере (session в БД)
- На клиенте (передаётся каждый раз)
- Гибридно

**Что нужно:** Определить ответственность.

## Как действовать

### Шаг 1: Определить границы

Что система делает, а что — НЕТ:
- Анализирует код? Да
- Исправляет код? Нет (только инструкции)
- Хранит историю? Да
- Работает offline? Нет

### Шаг 2: Определить роли

**Сервер:**
- Принимает задачу + контекст
- Анализирует через нейроны/граф
- Возвращает инструкции или вопросы

**Клиент:**
- Собирает контекст из проекта
- Отправляет на сервер
- Применяет инструкции локально
- Показывает вопросы пользователю

### Шаг 3: Определить минимальный набор

Что нужно для первого работающего цикла:

**На сервере:**
1. Endpoint для приёма запросов
2. Классификатор задач (простой, по ключевым словам)
3. Один нейрон для демонстрации
4. Формирование ответа

**На клиенте:**
1. Сбор package.json/composer.json
2. Отправка запроса
3. Вывод инструкций

**В протоколе:**
1. `new_task` — строка
2. `context` — объект
3. `outcome` — строка
4. `instructions` — массив строк

### Шаг 4: Итеративно расширять

После минимального цикла добавлять:
- Вопросы сервера
- RAG для поиска файлов
- Граф знаний
- Более сложные нейроны

## Ключевой вопрос

**Что сейчас есть в системе?**

Надо провести инвентаризацию:
1. Что реализовано на сервере?
2. Что реализовано на клиенте?
3. Что описано в протоколе?
4. Что работает end-to-end?

Только после инвентаризации можно понять, что делать дальше.
