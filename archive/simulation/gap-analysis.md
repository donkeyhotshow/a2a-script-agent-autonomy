# Gap Analysis: Симуляция vs Реальность

## Что показывает симуляция

Симуляция показывает **идеальный процесс**:
1. Клиент отправляет задачу + контекст
2. Сервер анализирует и возвращает инструкции
3. Процесс повторяется итеративно до завершения

## Что нужно для реализации

### На клиенте

| Компонент | Зачем нужен | Есть ли в системе? |
|-----------|-------------|-------------------|
| Сборщик package.json/composer.json | Для определения фреймворков и PSR-4 правил | ❌ Нет |
| Сканирователь PHP файлов | Для получения {path, namespace} | ❌ Нет |
| RAG индексатор | Для семантического поиска файлов | ⚠️ Есть в a2a-client/packages/rag/ |
| Применитель исправлений | Для изменения файлов по инструкциям | ❌ Нет |
| Обработчик вопросов | Для показа вопросов пользователю | ❌ Нет |

### На сервере

| Компонент | Зачем нужен | Есть ли в системе? |
|-----------|-------------|-------------------|
| Классификатор задач | Для определения mechanical vs semantic | ❌ Нет |
| Анализатор PSR-4 | Для проверки namespace | ❌ Нет |
| Генератор инструкций | Для формирования fixes[] | ⚠️ Есть нейроны, но не те |
| Система вопросов | Для уточнения контекста | ❌ Нет |
| Хранение контекста | Для итеративного процесса | ⚠️ Есть Prisma schema |

### В протоколе

| Элемент | Зачем нужен | Есть ли в системе? |
|---------|-------------|-------------------|
| `new_task` | Для передачи задачи | ⚠️ Есть в requirements.md |
| `context` | Для передачи состояния | ⚠️ Есть, но структура неясна |
| `questions` | Для уточнений | ❌ Нет |
| `scan_results` | Для результатов сканирования | ❌ Нет |
| `fixes` | Для инструкций по исправлению | ❌ Нет |
| `outcome` | Для статуса (need_files, completed) | ⚠️ Есть graph_incomplete/completed |

## Ключевой разрыв

**Симуляция предполагает, что:**
- Клиент умеет сканировать проект
- Сервер умеет анализировать PSR-4
- Протокол поддерживает вопросы и ответы

**Реальность:**
- RAG есть, но не используется для сканирования
- Нейроны есть, но они для детекции проблем, не для исправлений
- Протокол есть, но без вопросов и fixes

## Как подойти к вопросу

### Вариант 1: Сначала протокол

1. Определить полную структуру протокола
2. Реализовать на сервере
3. Реализовать на клиенте

**Проблема:** Долго, много кода до первого результата.

### Вариант 2: Сначала одна задача

1. Взять одну конкретную задачу (исправить импорты)
2. Реализовать только для неё
3. Обобщить потом

**Проблема:** Может не покрыть все случаи.

### Вариант 3: Минимальный цикл

1. Реализовать минимальный цикл: задача → контекст → инструкции
2. Без вопросов, без сложного протокола
3. Добавлять по необходимости

**Преимущество:** Быстрый старт, итеративное улучшение.

## Рекомендация

Начать с **Варианта 3**:
1. Клиент отправляет: `{new_task, package.json, composer.json}`
2. Сервер возвращает: `{outcome, instructions}`
3. Клиент применяет инструкции

Без вопросов, без итераций, без RAG. Просто механический анализ.
