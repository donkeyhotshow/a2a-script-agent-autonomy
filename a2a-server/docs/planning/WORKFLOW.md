# Planning Workflow

## Ідея

План — це не документ який пишуть один раз. Це жива структура яка проходить кілька раундів переосмислення перед тим як стати основою для коду. Агент бере активну роль: задає питання, пропонує варіанти, вибирає підхід, фіксує рішення. Людина коригує напрямок.

## Три раунди планування

### Раунд 1 — Розуміння
Що є зараз. Що працює, що зламано, що взагалі невідомо.
- Агент читає код і симуляції
- Задає питання по одному блоку
- Фіксує факти, не рішення

### Раунд 2 — Переосмислення
Чи правильно поставлена задача. Чи не можна простіше. Чи не суперечать issues одне одному.
- Агент перечитує всі issues і шукає протиріччя
- Пропонує об'єднати або розбити
- Перевіряє чи рішення в одному issue не ламає інше
- Результат: оновлені issues з явними залежностями

### Раунд 3 — Упаковка
Чи готово до реалізації. Чи є всі деталі. Чи зрозуміло з чого починати.
- Кожен issue повинен мати: проблему, рішення, конкретні дії, залежності
- Якщо чогось немає — issue не готовий до реалізації
- Результат: PRIORITIES.md з чітким порядком і блокуваннями

## Правила

- Агент не питає про очевидне — вибирає сам і пояснює чому
- Якщо рішення змінює інші issues — явно оновити їх
- Issues не видаляються — тільки оновлюється статус
- Симуляція = golden standard: спочатку симуляція, потім код (ADR-0001, ADR-0020)
- Перед реалізацією будь-якого issue — пройти всі три раунди
- Актуальні правила action-type ключів, трансформів та `execute`/`result` формату описані в [`AGENTS.md`](../../../AGENTS.md); перед змінами плану перевірте, чи там не оновилися критичні інструкції, і при потребі вкажіть, який розділ AGENTS змінився.

## Статуси issues

| Статус | Значення |
|--------|----------|
| `потребує перевірки` | Є гіпотеза, треба перевірити в коді |
| `потребує аудиту` | Треба прочитати і порівняти |
| `заплановано` | Рішення є, реалізація не почата |
| `стратегія визначена` | Підхід узгоджений, треба зробити в симуляціях |
| `потребує переробки` | Є старий варіант, треба переробити під нову стратегію |
| `в роботі` | Активна розробка |
| `КРИТИЧНО` | Блокує інші задачі, виконати першим |
| `завершено` | Реалізовано і перевірено на симуляції |

## Порядок роботи з симуляцією

Канонічні фікстури: каталог **`simulations/<імʼя>/` у корені репозиторію** (див. [`REFERENCE.md`](REFERENCE.md)). Не дублювати кроки симуляцій у `docs/`.

```
1. Прочитати симуляцію (всі кроки)
2. Визначити які transforms потрібні
3. Перевірити чи transforms існують в prompts/transforms/
4. Написати/виправити код
5. Запустити: node a2a-server/scripts/run-simulation.ts <name>
6. Порівняти output з response.json кожного кроку
```

## Ознаки що issue готовий до реалізації

- Є конкретна симуляція яка описує очікувану поведінку
- Є список файлів які треба змінити
- Немає відкритих питань які блокують рішення
- Залежності від інших issues явно вказані і вирішені або прийняті
