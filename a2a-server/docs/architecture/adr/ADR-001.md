# ADR-001: Архитектура A2A Script Agent

## Дата
2026-02-25

## Авторы
- Команда разработки

## Статус
Принято

## Контекст

A2A Script Agent — это система Agent-to-Agent для интеллектуального анализа кодовой базы. Проект состоит из двух основных компонентов:

### a2a-server
Серверная часть, реализующая протокол A2A:
- **Runtime:** Node.js 20+
- **Language:** TypeScript
- **Framework:** Express
- **Database:** PostgreSQL + pgvector
- **Cache/Queue:** Redis + BullMQ
- **ML:** Plexe
- **Git:** simple-git

### a2a-client
Клиентская часть, включающая:
- Web UI для взаимодействия с пользователем
- Набор npm-пакетов: `agent`, `api-client`, `fs-utils`, `rag`, `script-runner`
- E2E тесты на Playwright
- Интеграционные тесты на Vitest

## Ключевые архитектурные решения

### 1. Stateless Server Design
Сервер **не хранит данные клиента**. Graph передаётся в контексте и возвращается в ответе:
- Server получает контекст и **может модифицировать** его
- Client хранит индексы (RAG, file search, free-form search)
- Client отправляет контекст обратно серверу **без изменений** (только добавляет новые данные: `step_result`, `code_blocks`)

### 2. PhaseMachine
State machine управляет потоком запросов:
```
idle → discovery → recognition → analysis → action → validation → completed
```

### 3. ActionProcessor (no-AI mode)
Действия, определённые в MD файлах под `a2a-server/src/actions/definitions/`, выполняются без AI вызовов.

### 4. Timer-based Request Processor
Опрос pending запросов каждые 5 секунд (настраивается через `REQUEST_PROCESSOR_INTERVAL_MS`).

## Разделение ответственности

### Client
- Хранит все индексы кодовой базы (RAG, file search, free-form search)
- Хранит историю
- Выполняет команды из ответов сервера
- Отправляет контекст обратно серверу без изменений

### Server
- Управляет клиентом через payload ответа
- Не хранит пользовательский код или данные кодовой базы
- Не использует кэши для передачи данных между итерациями
- `fileCachePath` — только для серверных ассетов (например, git clone dirs)

## API Endpoints

### Auth
- `POST /api/v1/auth/register` - Регистрация клиента
- `POST /api/v1/auth/token` - Получение JWT токена
- `POST /api/v1/auth/refresh` - Обновление токена
- `GET /api/v1/auth/me` - Текущий пользователь

### Requests (Async Protocol)
- `POST /api/v1/requests` - Создать запрос, возвращает `promiseId`
- `GET /api/v1/requests/:promiseId/status` - Статус запроса
- `GET /api/v1/requests/:promiseId/result` - Результат (completed/failed)
- `DELETE /api/v1/requests/:promiseId` - Отменить запрос

### Sessions
- `POST /api/v1/sessions` - Создать сессию
- `GET /api/v1/sessions` - Список сессий
- `GET /api/v1/sessions/:sessionId` - Получить сессию
- `PATCH /api/v1/sessions/:sessionId` - Обновить сессию
- `DELETE /api/v1/sessions/:sessionId` - Удалить сессию

## Требования к конфигурации

- **JWT_SECRET** — минимум 32 символа (валидация через Zod)
- **ENCRYPTION_KEY** — ровно 32 символа (для тестов)
- Все конфигурации через переменные окружения
