# Известные проблемы и ограничения модуля Landing Page

Данный документ описывает текущие ограничения и особенности реализации модуля Landing Page (на примере
`storage/aiInstaller/landing-main-page/`).

## Ограничения Функциональности

### 1. Отсутствие Серверных Действий и Нефункциональные Формы

**Описание:**
Модуль имеет базовую структуру `UI`, включая формы (контакты, запись), но **не включает серверные действия (`actions`)**
для их обработки. Кнопки отправки в формах **неактивны** (не имеют `customHooks` или атрибутов `on` для отправки
данных).

**Затронутые компоненты:**

- Формы обратной связи (`contact.json`)
- Формы записи (`booking.json`)
- Кнопки выбора тарифов (`pricing-section.json`)
- Кнопка "Дивитися більше в Instagram" (`services.json`)

**Пример нефункциональной кнопки отправки (из `booking.json`):**
<!-- ```json
{
  "type": "Button",
  "props": {
    "label": "Записатися на сеанс", // Кнопка есть
    "class": "w-full cursor-pointer"
  }
  // Отсутствуют customHooks или on для отправки данных
}
``` -->

**Что требуется для реализации:**

- Создание директории `actions/` с `JSON`-файлами инструкций (или `PHP`-файлами).
- Добавление `customHooks` или атрибутов `on` к кнопкам форм для вызова серверных действий.
- Реализация серверной логики (валидация, отправка email/сохранение данных).
- Возможная интеграция с `FormManager` для управления состоянием формы.

### 2. Отсутствие модальных окон и диалогов

**Описание:**
Текущая реализация модуля **не содержит** модальных окон (`Dialog`) или сложных всплывающих элементов. Любые необходимые
подтверждения или дополнительная информация должны отображаться на отдельных страницах или статично.

**Отсутствующие компоненты (для возможной доработки):**

- Диалоговые окна подтверждения.
- Модальные формы.
- Попапы с детальной информацией.

**Что требуется для реализации:**

- Создание `JSON`-структур для модальных окон.
- Использование `ModalManager` и компонента `Dialog`.
- Реализация логики показа/скрытия через `customHooks` или `actions`.

### 3. Ограниченная интеграция с другими модулями

**Описание:**
Модуль Landing Page является **самодостаточным** и имеет минимальную интеграцию с другими модулями, особенно с теми, что
требуют состояния авторизации или серверной логики (например, `Login Form`). Навигация к другим модулям осуществляется
через простые ссылки/`navigateTo`.

**Текущие ограничения интеграции:**

- Отсутствие реакции на изменение состояния авторизации (например, показ имени пользователя).
- Отсутствие передачи данных в другие модули или получения данных из них (кроме как через URL).

**Что требуется для реализации (если необходимо):**

- Реализация подписки на события `NotifyManager` (например, для обновления `UI` при логине/логауте).
- Использование `StateManager` (`hub`) для обмена данными.
- Вызов действий других модулей.

## Технические Особенности Реализации

### 1. Статический контент

**Описание:**
Основная часть контента в модуле **статична** и встроена непосредственно в `JSON`-файлы страниц и секций. Возможно
использование директории `data/`, но нет механизма загрузки из `БД` или `API`.

**Особенности:**

- Контент (тексты, пути к изображениям) прописан в `JSON`.
- Отсутствует привязка к динамическим источникам данных.
- Обновление контента требует редактирования `JSON`-файлов модуля.

**Пример статического контента (из `header-section.json`):**
<!-- ```json
{
  "type": "Tag",
  "props": {
    "content": "<span class='font-medium text-2xl ...'>barberxxl.com.ua</span>",
    ...
  }
}
``` -->

**Что требуется для реализации (если необходимо):**

- Реализация механизма загрузки контента из CMS, `API` или `БД`.
- Использование моделей данных (`models/`).
- Возможно, кэширование.

### 2. Базовая адаптивность

**Описание:**
Адаптивность реализована в основном через классы **`Tailwind CSS`** (например, `md:grid-cols-3`, `lg:hidden`). Сложные
случаи или специфические разрешения могут требовать доработки.

**Потенциальные области для улучшения:**

- Мобильное меню (хотя в `barber-and-tattoo` оно базово реализовано).
- Отображение сложных сеток на очень маленьких экранах.
- Перенос/скрытие блоков на разных разрешениях.

**Что требуется для улучшения:**

- Тщательное тестирование на разных устройствах. # //ТЕСТЫ НА ПОТОМ
- Возможно, использование более сложных `CSS`-техник или `JS` для адаптивности.

### 3. Оптимизация ресурсов

**Описание:**
**Не уделяется особого внимания** оптимизации загрузки ресурсов (изображений, `JSON`).

**Особенности:**

- Отсутствие ленивой загрузки (lazy loading) изображений или секций.
- Все секции, включенные в страницу, загружаются и парсятся сразу.

**Что требуется для улучшения:**

- Реализация lazy loading для изображений (`loading="lazy"` атрибут или `JS`).
- Возможно, динамическая подгрузка секций по мере скролла.
- Оптимизация размера изображений.

## Прочие Особенности

### 1. Отсутствие централизованного состояния

**Описание:**
Модуль **не использует** централизованное управление состоянием (`StateManager`/`hub`). Любое состояние является
локальным для компонента (например, состояние `Accordion` или `Tabs`).

**Ограничения:**

- Нет возможности передавать состояние между несвязанными секциями или страницами.

**Что требуется для реализации (если необходимо):**

- Использование `hub.get()`, `hub.update()` для доступа и изменения глобального состояния.

### 2. Отсутствие Тестов

**Описание:**
**Не включены** автоматизированные тесты. # //ТЕСТЫ НА ПОТОМ

**Что требуется для реализации:**

- Разработка юнит-тестов и интеграционных тестов.
