# Задание: Доработка и развитие модуля Login Form (v1)

## 1. Описание и цели

Модуль login-form должен обеспечивать:
- Надежную авторизацию пользователя (логин по паролю) — реализовано.
- Возможность регистрации нового пользователя (расширение).
- Восстановление пароля (расширение).
- Корректную обработку ошибок и валидацию.
- Переадресацию пользователя после успешной авторизации/регистрации/выхода/сброса пароля.
- Информационные страницы для различных состояний (не авторизован, выход, сброс пароля и др.).

---

## 2. Детальный план процессов

### 2.1. Авторизация (реализовано)
- Форма логина принимает имя пользователя и пароль.
- После отправки формы:
  - Выполняется валидация (login-validation.json).
  - В случае успеха — вызывается authenticate.json, пользовательские данные пишутся в session:user.
  - (требует реализации) После успешной аутентификации инициируется переадресация пользователя на защищенную страницу (или dashboard).
  - (требует реализации) В случае ошибки — отображается сообщение об ошибке.

### 2.2. Регистрация (требует реализации)
- Форма регистрации должна быть реализована как отдельная вкладка или страница.
- После отправки формы:
  - Выполняется валидация (registration-validation.json).
  - В случае успеха — создается новый пользователь, автоматически выполняется вход и переадресация.
  - В случае ошибки — отображается сообщение об ошибке (например, пользователь уже существует).
- Необходимые шаги:
  1. Описать структуру данных для регистрации (минимум: username, password, email).
  2. Реализовать action/command для создания пользователя.
  3. Интегрировать регистрацию в общий процесс аутентификации (автоматический вход после регистрации).
  4. Добавить обработку ошибок (существующий пользователь, слабый пароль и т.д.).
  5. Реализовать переадресацию после успешной регистрации.

### 2.3. Восстановление пароля (требует реализации)
- Форма восстановления пароля должна быть реализована как отдельная вкладка или страница.
- После отправки формы:
  - Выполняется валидация email/username.
  - В случае успеха — отправляется письмо с инструкцией по сбросу пароля (или генерируется временный пароль).
  - После сброса пароля — пользователь перенаправляется на страницу подтверждения или логина.
  - В случае ошибки — отображается сообщение об ошибке.
- Необходимые шаги:
  1. Описать структуру данных для восстановления (email или username).
  2. Реализовать action/command для генерации и отправки инструкции по сбросу.
  3. Реализовать action/command для сброса пароля (reset-password.json).
  4. Добавить обработку ошибок (несуществующий пользователь, ошибка отправки письма и т.д.).
  5. Реализовать переадресацию после успешного сброса пароля.

### 2.4. Переадресация (требует доработки)
- После успешной авторизации или регистрации пользователь должен быть перенаправлен на целевую страницу (dashboard, профиль и т.д.).
- После выхода — на страницу логина или информационную страницу "Выход выполнен".
- После сброса пароля — на страницу подтверждения или логина.
- Переадресация должна быть реализована через событие (userAuthenticated, userLoggedOut) или через изменение session:user.
- Необходимые шаги:
  1. Описать сценарии переадресации для всех процессов.
  2. Реализовать механизм событий или наблюдения за session:user.
  3. Добавить обработку переадресации в actions/commands.
  4. Проверить корректность работы во всех сценариях.

### 2.5. Информационные страницы (требует реализации)
- Страница "Вы не авторизованы" (если пользователь пытается попасть на защищенную страницу).
- Страница "Выход выполнен".
- Страница "Пароль успешно сброшен".
- Сообщения об ошибках и успехе должны быть видимы и понятны пользователю.
- Необходимые шаги:
  1. Описать сценарии отображения информационных страниц.
  2. Реализовать отдельные страницы или секции для каждого состояния.
  3. Интегрировать отображение сообщений в общий процесс.

## 3. Критерии приемки

- Все процессы (логин, регистрация, восстановление, выход, сброс пароля) реализованы и покрыты user stories.
- Переадресация работает для всех сценариев.
- Ошибки и успехи отображаются пользователю.
- Нет устаревших или неиспользуемых файлов/компонентов.
- Документация и структура соответствуют стандартам.

## 5. Детальное описание UI: Страница "Вход" (логин)

### 5.1. Структура страницы/вкладки "Вход"

- **Заголовок**: "Вход в систему" (или аналогичный)
- **Поля формы**:
  - Имя пользователя (или email)
  - Пароль
- **Кнопка**: "Войти"
- **Ссылка**: "Забыли пароль?" (переключает на восстановление)
- **Область для сообщений об ошибках/успехе**

### 5.2. Логика и поведение

- Все поля обязательны для заполнения.
- При отправке формы:
  - Выполняется валидация на клиенте (не пусто).
  - Если ошибка — показать сообщение об ошибке под соответствующим полем или в общей области ошибок.
  - Если валидация пройдена — отправить данные на сервер (action/command).
  - На время отправки:
    - Кнопка "Войти" становится неактивной (disabled).
    - Отображается loader/индикатор загрузки.
- После ответа сервера:
  - В случае успеха:
    - Инициировать событие/механизм переадресации на защищенную страницу (dashboard и т.д.).
  - В случае ошибки:
    - Показать сообщение об ошибке (например, "Неверный логин или пароль").
    - Кнопка "Войти" снова активна.

### 5.3. UX/доступность

- Фокус на первом поле при открытии страницы.
- Возможность отправки формы по Enter.
- Сообщения об ошибках доступны для скринридеров (aria-live).
- Адаптивная верстка: форма по центру, корректно отображается на мобильных и десктопах.
- Кнопка "Войти" визуально выделена.
- Ссылка "Забыли пароль?" легко доступна.

### 5.4. Переходы

- Клик по "Забыли пароль?" — переключение на страницу/вкладку восстановления пароля без перезагрузки.
- После успешного входа — переадресация на dashboard или целевую страницу.
- После неудачного входа — остается на странице, отображается ошибка.
