# Strict Module Structure Checklist

> Этот чеклист обязателен для всех модулей, обрабатываемых системой. Расширяется по мере изучения новых требований и
> паттернов. Все пункты должны быть выполнены для успешной работы процессоров и валидации.

## 1. Обязательные директории (даже если пустые)

- [ ] docs/
- [ ] actions/
- [ ] templates/
- [ ] code/
- [ ] validations/
- [ ] data/
- [ ] pages/
- [ ] state/
- [ ] commands/
- [ ] _i/
- [ ] assets/ (если нужны)

## 2. Документация (`docs/`)

- [ ] `README.md` — обзор, цель, основные возможности, пользовательские сценарии.
- [ ] `index.md` — структура документации модуля, ссылки на ключевые разделы и внешние стандарты.
- [ ] `known-issues.md` — актуальный список известных проблем, их статус и временные/постоянные решения.
- [ ] `code.md` — описание структуры PHP-кода модуля, ключевых классов и их взаимодействия с JSON-конфигурациями (если
  применимо).
- [ ] `data-schema.md` — описание структур данных, используемых и обрабатываемых модулем (в `data/`, `pages/`,
  `actions/`).
- [ ] `changelog.md` — история изменений модуля.
- [ ] Все внутренние и внешние ссылки в документации актуальны и ведут на существующие ресурсы/стандарты.
- [ ] Отмечено отсутствие ранее упомянутых, но не найденных внешних стандартов (например, `module-verification.md`,
  `component-standards.md`), если применимо.
- [ ] **JSON-файлы в `docs/`**: Если в директории `docs/` присутствуют файлы формата `.json`, они, как правило,
  пропускаются валидатором модулей. Наличие ключа `type` на корневом уровне таких файлов излишне и может быть удалено.

## 3. PHP Класс Модуля (`code/ИмяМодуля.php`)

- [ ] Присутствует основной PHP класс модуля (например, `code/ИмяМодуля.php`).
- [ ] Класс наследуется от подходящего базового класса (например, `App\AiRudeDepot\App\App` или
  `App\AiRudeDepot\Modules\PageModule`).
- [ ] Класс содержит публичное свойство `public $folder = 'имя-папки-модуля';`, значение которого точно соответствует
  имени директории модуля.
- [ ] Если класс модуля содержит бизнес-логику, она актуальна и не закомментирована без причины.

## 4. Метаданные и индексы (`_i/`)

**Директория `_i/` является обязательной для обнаружения модуля инсталлятором.** Она содержит файлы метаданных и
конфигурации для **AI Инсталлятора**.

- [ ] `_i/meta.json` присутствует и содержит как минимум:
    - [ ] `name` (читаемое имя модуля, используется как метка в инсталляторе)
    - [ ] `version` (версия модуля)
    - [ ] `description` (краткое описание)
    - [ ] `author` (автор/команда)
    - [ ] `dependencies` (актуальные фронтенд-зависимости, например, PrimeVue, Tailwind)
- [ ] **Инсталлятор-специфичные файлы в `_i/`**: Эти файлы используются **AI Инсталлятором** для определения, как модуль
  должен быть установлен и интегрирован. Наличие этих файлов определяет, какие возможности инсталлятора будут применены
  к модулю.
    - [ ] `_i/files-by-block.json` (Обычно присутствует): Корректно описывает структуру файлов модуля для инсталлятора и
      последующей работы рантайм-системы:
        - **Назначение для инсталлятора**: Определяет выбираемые ''блоки'' или ''компоненты'' модуля, которые
          пользователь может установить.
            - Верхнеуровневые ключи в этом файле (например, `code`, `actions`, `templates`) становятся элементами
              выбора (чекбоксами) в инсталляторе.
            - Значения, связанные с этими ключами, представляют собой JSON-структуры, описывающие файлы и поддиректории
              для данного блока. Эта структура обрабатывается логикой, подобной `extractFilePaths` (где ключи JSON
              формируют пути к поддиректориям, а строковые значения или массивы строк — имена файлов).
        - **Соответствие рантайм-ожиданиям**: Установленные файлы из этих блоков должны формировать структуру
          директорий (например, `actions/`, `data/`, `templates/`), которую ожидает рантайм PHP-система модуля (классы
          `App.php`, `PageModule.php` и специфичный для модуля PHP-класс). Рантайм-система (например,
          `PageModule::moduleRun`, `App::moduleActions`) использует свойство `$folder` в PHP-классе модуля (которое
          должно соответствовать имени папки модуля) для построения путей к файлам внутри этих директорий (например,
          `[module-slug]/pages/[pagePath].json`).
        - **Основные блоки (конвенции)**: Следующие ключи являются общепринятыми и отражают стандартные директории,
          ожидаемые рантайм-системой:
            - [ ] `code` (основной PHP класс модуля и связанные PHP файлы)
            - [ ] `actions` (JSON-файлы инструкций для клиент-серверного взаимодействия)
            - [ ] `commands` (JSON-файлы серверных команд)
            - [ ] `templates` (JSON-файлы UI-шаблонов или компонентов)
            - [ ] `pages` (JSON-файлы описания страниц модуля)
            - [ ] `data` (JSON-файлы с данными, включая `blanks`, `models` и т.д.)
            - [ ] `validations` (JSON-файлы правил валидации)
            - [ ] `state` (JSON-файлы начального состояния, например, `validationErrors.json`)
            - [ ] `docs` (файлы документации модуля)
            - [ ] `assets` (статические ресурсы: изображения, стили, скрипты)
            - [ ] `_i` (внутренние метаданные и конфигурации самого модуля, если часть из них должна быть скопирована)
    - [ ] `_i/common.json` (Опционально, используется инсталлятором): Определяет ключевые файлы модуля по категориям для
      инсталлятора. Структура JSON-содержимого обрабатывается логикой, подобной `extractFilePaths`.
    - [ ] `_i/links.json` (Опционально, используется инсталлятором): Определяет перманентные ссылки/роуты для модуля.
      Должен быть массивом объектов, где каждый объект описывает ссылку со свойствами: `id` (идентификатор), `type` (
      тип/категория ссылки, например, `guest`), `label` (отображаемый текст), `path` (URL путь), `page` (имя файла
      страницы в `pages/` без `.json`), `icon` (класс иконки).
    - [ ] `_i/css.json` (Опционально, используется инсталлятором): Конфигурация для обработки CSS модуля.
    - [ ] `_i/meta-admin.json` (Опционально, используется инсталлятором): Дополнительные метаданные, возможно, для
      админ-панели.
    - [ ] `_i/useAnyway.json` (Опционально, часто присутствует, но его конкретная роль или ожидаемая схема не полностью
      ясны из текущих эталонов; может быть пустым объектом `{}`). Прямое использование в основном PHP-коде
      инсталлятора (`InstallerController.php`) не обнаружено при анализе. Его точная, принудительно используемая роль в
      процессе установки остается неподтвержденной.
    - [ ] Другие `.json` файлы в `_i/` могут использоваться для специфических нужд инсталлятора или других
      инструментов (требуют проверки).

## 5. Файлы состояния (`state/`)

- [ ] Если используются файлы состояния (например, `state/validationErrors.json`):
    - [ ] Они корректно описаны в `_i/files-by-block.json` (в секции `main` под ключом `state`).
    - [ ] Файлы присутствуют в директории `state/`.
    - [ ] Их содержимое соответствует начальному или ожидаемому состоянию.

## 6. Конфигурация страниц (`pages/`)

- [ ] JSON-файлы страниц (например, `pages/main.json`) корректно структурированы.
- [ ] **`type` страницы**: Корневой `type` должен быть `"Page"` (или `"page"` в нижнем регистре, если это соответствует
  актуальной схеме валидации `install-modules/aiCore/validation/components/P/Page.json`).
- [ ] **Соответствие схеме страницы**: Страница должна содержать все обязательные для её типа ключи (например, `content`
  для основного содержимого, корректно указанный `layout`, если требуется).
- [ ] Используемые макеты (`layout`) существуют и правильно подключены.
- [ ] Операции `{"type": "operation", "action": "include", "source": "..."}`:
    - [ ] Корректно используются для вставки других JSON-структур.
    - [ ] Адрес `source` (адрес в `DataHub`) указан правильно и ресурс доступен. Этот тип операции обрабатывается
      процессором `WalkForOperations.php`.
- [ ] Операции `{"type": "operation", "action": "add", "source": "..."}`:
    - [ ] Корректно используются для добавления элементов в массив.
    - [ ] Адрес `source` (адрес в `DataHub`) указан правильно и ресурс доступен. Этот тип операции обрабатывается
      процессором `WalkForOperations.php`.
- [ ] Операции `{"type": "operation", "action": "remove"}` используются корректно. Этот тип операции обрабатывается
  процессором `WalkForOperations.php`.
- [ ] Для форм используется корректная модель привязки `{"model": {"form": "имя_файла_данных_формы"}}`. Процессор
  `WalkForForms.php` использует это для загрузки начальных данных формы из `data/` и слияния ошибок валидации из
  `buffer:validationErrors` в структуру формы.

## 7. Файлы данных (`data/`)

- [ ] JSON-файлы данных (например, для форм `data/my-form-data.json`) корректно структурированы.
- [ ] Пути к файлам данных, используемые в `pages/` (через `model.form`) или `actions/`, указаны правильно.
- [ ] Структура данных соответствует ожиданиям компонентов UI и логики обработки.
- [ ] **Шаблоны данных UI (`ui_data_maps`)**: Файлы, представляющие собой карты или шаблоны данных для UI (ранее могли
  находиться в `templates/ui_data_maps/`), должны быть перемещены в директорию `data/`. Рекомендуется давать им суффикс
  `.template.json`.
- [ ] **Отсутствие `type` в файлах данных**: Как правило, JSON-файлы в `data/` не должны содержать ключ `type` на
  корневом уровне, если это не требуется специфической схемой данных, которой они должны соответствовать. Внутренние
  ключи `type` в секциях данных (например, в перемещенных `ui_data_maps`) также должны быть удалены, если они не служат
  специальной цели, понятной системе.

## 8. Actions и Commands (`actions/`, `commands/`)

- [ ] JSON-инструкции в `actions/*.json` и `commands/*.json` имеют корректный синтаксис. Эти файлы содержат инструкции
  для центрального движка обработки инструкций (`StorageHelper::executeInstructions/processInstruction`), который
  вызывается через `DataProcessor::processActionFile()` после того, как `App::moduleActions` определит файл действия по
  `sendTo`.
- [ ] **Типизация `actions/*.json`**:
    - [ ] Если файл определяет серверное действие, которое не является UI-компонентом, подходящим `type` может быть
      `"actionDefinition"` (или `"action"` в нижнем регистре, если это соответствует схеме
      `install-modules/aiCore/validation/components/A/Action.json`).
    - [ ] Если файл описывает структурированный набор инструкций (не UI), и для него существует схема типа
      `"Instructions"` (см. `docs/guides/module-validation-guide.md`), то должен использоваться этот `type` с
      обязательным наличием массива `instructions: []` и других требуемых полей.
        - **Новое требование (по результатам валидации)**: Для файлов с `type: "Instructions"` (или аналогичных, представляющих набор инструкций) валидатор может требовать наличие ключа `tags` на корневом уровне. Этот ключ должен быть объектом следующей структуры (даже если значения остаются пустыми/по умолчанию):
          ```json
          "tags": {
            "keywords": [],     // Массив ключевых слов
            "ai_summary": "",   // Строка для AI-генерируемого описания
            "features": []      // Массив строк, описывающих функциональность
          }
          ```
- [ ] Используются правильные и осмысленные значения для полей:
    - [ ] `action` (например, `update`, `save`, `for`, `call`, `return`, `print_r`) - определяет тип инструкции для
      движка.
    - [ ] `from` / `address` (источник данных, адрес в `DataHub`) - указывает, откуда брать данные.
    - [ ] `value` (прямое значение) - прямое значение данных.
    - [ ] `to` (целевой адрес в `DataHub`) - указывает, куда сохранять результат.
    - [ ] `condition` (условие выполнения) - используется `DataManipulateHelper::evaluateCondition`.
        - **Важно по `condition`**:
            - PHP-рантайм (`DataManipulateHelper::evaluateCondition`) обрабатывает строковые условия как **прямые
              DataHub пути** (например, `"buffer:myFlag"`, `"!buffer:anotherFlag"`). Он **не парсит** сложную логику (
              например, `&&`, `||`) из строк.
            - Комплексная логика (`AND`, `OR`, сравнения и т.д.) **должна** быть выражена через **массивный синтаксис
              ** (например, `["and", "buffer:pathA", "buffer:pathB"]`, `["equals", "buffer:valueA", "literalValueB"]`).
            - Валидатор JSON (`php artisan validate:module-json`) может использовать регулярное выражение для строковых
              условий, которое может пропустить сложные выражения в фигурных скобках (например,
              `"{buffer:valA && buffer:valB}"`), но такие условия **не будут корректно работать в PHP-рантайме**.
            - На данный момент `DataManipulateHelper.php` может не поддерживать все желаемые логические операторы в
              массивном синтаксисе (например, `OR`). В таких случаях может потребоваться доработка хелпера или
              реструктуризация логики JSON.
    - [ ] `keyPath` (путь к ключу внутри данных)
    - [ ] `with` (трансформация данных) - используется `DataManipulateHelper::applyDataTransformation`.
    - [ ] `find` (параметры поиска) - используется `DataManipulateHelper::searchInData`.
    - [ ] `instructions` (для вложенных инструкций в `for`, `call`)
    - [ ] `disabled` (для временного отключения инструкции)
- [ ] Адресация `DataHub` используется корректно:
    - [ ] Правильные префиксы типов хранилищ (например, `file!`, `buffer:`, `model!`, `session!`, `args!`, `input!`,
      `output!`, `registry!`, `config!`). Эти адреса разрешаются через API, предоставляемое `InstructionProcessor.php` (
      методы `get`, `set`, `save`, `remove`, `find`), который взаимодействует с `DataHub`.
    - [ ] Корректные пути к ресурсам. Например, `file!modules/{$this->getSlug()}/data/filename.json` для доступа к файлу
      данных модуля.
    - [ ] Плейсхолдеры `{адрес_в_DataHub}` используются правильно и разрешаются в ожидаемые значения движком инструкций.
- [ ] Логика инструкций соответствует цели действия/команды.
- [ ] Предусмотрена обработка ошибок (например, через `condition` или запись в `buffer:validationErrors`).

## 9. Работа с состоянием и данными (общие принципы)

- [ ] **DataHub как центральный механизм**: `DataHub` является центральным хранилищем и механизмом обмена данными между
  различными частями системы (UI, PHP-классы модулей, обработчики инструкций, процессоры). Доступ к нему осуществляется
  через API, предоставляемое `InstructionProcessor.php`.
- [ ] Четко определены и консистентно используются механизмы работы с сессией пользователя (например, `session:user`,
  `localStorage`, `DataHub` буферы типа `buffer:userSessionData`). `session!` префикс в `DataHub` напрямую работает с
  механизмом сессий.
- [ ] Четко определены и консистентно используются механизмы работы с моделями данных (например, `model!ИмяМодели`,
  `file!path/to/data.json`, `DataHub` адресация). `model!` работает с моделями ORM (через
  `DataManipulateHelper::simulateCreateInstance` и подобные), `file!` работает с файловой системой.
- [ ] Учтены известные проблемы с надежностью некоторых хранилищ (например, `session!`, `model!`) и применены
  рекомендованные обходные пути, если это необходимо.
- [ ] Используемые буферы `DataHub` (например, `input`, `output`, `args`, `buffer:validationErrors`, `buffer:for.*`,
  `buffer:actionResult`) используются по назначению.
- [ ] Передача данных из UI в Actions происходит через `input!`, параметры вызова команд/инструкций через `args!`,
  результаты сохраняются в `output!` или напрямую в другие `DataHub` адреса.
- [ ] `model` (Для VModel компонентов)
    - [ ] Используется для компонентов, взаимодействующих с `FormManager` (например, `inputtext`, `select`, `checkbox`).
    - [ ] Должен содержать `form` (String, имя формы) и `field` (String, имя поля в форме).
    - [ ] Для `select` и подобных компонентов, если опции загружаются динамически, `model.options` должен содержать
      `{ "action": "include", "type": "operation", "source": "адрес/в/datahub" }`.
    - [ ] **Примечание по валидации `Select`**: Валидатор может некорректно помечать стандартные и необходимые свойства
      для компонента `Select` (например, `props.options`, `props.optionLabel`, `props.optionValue`, `props.required`,
      `props.showClear`) как неизвестные. Перед удалением таких свойств следует свериться с документацией компонента и
      его предполагаемой функциональностью, так как проблема может быть в неполноте схемы валидатора.

## 10. Валидация (`validations/`)

- [ ] JSON-файлы правил валидации (например, `validations/my-rules.json`) корректно структурированы.
- [ ] Правила валидации соответствуют проверяемым данным.
- [ ] Результаты валидации корректно сохраняются (например, в `buffer:validationErrors`, `buffer:validationFailed`).
- [ ] **Специфика валидации файлов определений**: Файлы, описывающие правила валидации (например,
  `my-form.validation.json`), предназначены для определения правил, а не для описания UI-компонентов. Валидатор модулей
  может ошибочно применять к ним UI-схемы, что приведет к ошибкам типа "Node at 'root' is missing or has an invalid '
  type'" или "Disallowed component type: 'required'" (где 'required' является типом правила, а не UI-компонента). Это
  следует учитывать при анализе ошибок валидации таких файлов.

## 11. Зависимости и окружение

- [ ] Учтена интеграция с бэкенд-фреймворком (например, Laravel для email, Socialite, специфических путей), если это
  требуется для работы модуля.

## 13. Общее качество кода и конфигураций

- [ ] Отсутствует избыточный, закомментированный или неиспользуемый код/конфигурации (если это не сделано намеренно с
  комментарием).
- [ ] Наименования файлов, ключей в JSON, переменных соответствуют стандартам и понятны.
- [ ] Структура JSON-файлов легко читаема и логична.
- [ ] **Динамический `type` компонента**: При использовании динамического значения для `type` компонента (например,
  `"type": "{buffer:for.currentItem.type}"` при генерации UI), следует учитывать, что валидатор может пометить это как
  ошибку. Необходимо убедиться, что такая динамическая типизация поддерживается системой рендеринга и соответствующими
  схемами валидации.

### 3.1. `type` (Обязательно)

- [ ] **Правила определения Регистра для `type` компонента (критично для валидатора и рендеринга):**
    - [ ] **Стандартные HTML элементы**: Должны быть указаны в **нижнем регистре** (e.g., `div`, `h2`, `p`, `span`,
      `img`, `a`). Валидатор и система рендеринга ожидают именно такой регистр.
    - [ ] **Vue компоненты (включая PrimeVue и кастомные)**: Для UI JSON, где компонент маппится через
      `install-modules/aiCore/js/component-map.json` (или его дочерние карты), `type` **должен соответствовать ключу в
      этой карте (обычно нижний регистр)**. Например, `inputtext`, `button`, `panel`. Для компонентов, не проходящих
      через такой маппинг или если схема валидатора явно указывает PascalCase, используется PascalCase (e.g. `Page`). *
      *Приоритет у актуальных схем валидации и `component-map.json`.**
    - [ ] **Проверка по `component-map.json`**: Убедиться, что используемый `type` (и его регистр) для компонентов
      PrimeVue и кастомных оберток соответствует записям в `install-modules/aiCore/js/component-map.json` и связанным
      картам (`v-model-component-map.json`, `component-containers-map.json`).
    - [ ] **Соответствие файлам правил валидации**: Имя файла правила (например,
      `install-modules/aiCore/validation/components/P/Panel.json`) и `componentName` внутри него определяют ожидаемый
      `type`. Часто для HTML-подобных элементов правила ожидают `type` в нижнем регистре, для комплексных компонентов
      PrimeVue - в PascalCase или как указано в `componentName`.
    - [ ] **Общая обновленная рекомендация**: Для стандартных HTML-тегов используйте **нижний регистр**. Для компонентов
      PrimeVue и кастомных оберток сверяйтесь с `component-map.json` (предпочтение ключам в нижнем регистре, если они
      там так определены) и соответствующими схемами валидации. Если схема валидации ожидает PascalCase (например, для
      `Page`), используйте его.
- [ ] **Не использовать** устаревшее поле `_element`.

### 3.2. `props` (Свойства компонента)

- [ ] Все передаваемые `props` должны быть валидны для данного `type` компонента (см. документацию PrimeVue или
  обертки).
- [ ] Ссылки на данные из `StateManager/hub` (который синхронизируется с `DataHub` на бэкенде) должны использовать
  корректный синтаксис: `"{путь/к/данным}"` или `"{state:путь/к/данным/в/hub}"`.
- [ ] Классы Tailwind CSS указываются в `props.class`.
- [ ] **Отсутствие `props.name` для InputText/Textarea**: Если для `InputText` или `Textarea` используется `model.form`
  и `model.field` для привязки данных, и валидатор выдает ошибку "Unknown property 'name'", свойство `name` из `props`
  следует удалить.
- [ ] **Корректность `props.severity` для `Button`**: Убедиться, что значение `props.severity` для компонента `Button`
  является одним из допустимых (`primary`, `secondary`, `success`, `info`, `warn`, `help`, `danger`, `contrast`). Для "
  контурного" стиля использовать `props.variant="outlined"` (если поддерживается).
- [ ] **Соответствие типов компонентов**: Убедиться, что используются корректные `type` для компонентов, например,
  `datatable` вместо `TaskList`, `form` вместо `TaskForm`, если это ожидается системой рендеринга/валидации.
- [ ] **Отсутствие неизвестных ключей**: Проверить, что в `props` или на верхнем уровне компонента не используются
  ключи, неизвестные валидатору для данного типа компонента (например, пользовательский ключ `footer`, если он не
  является стандартным слотом/свойством).

### 3.3. `children` и `items` (Дочерние компоненты)

- [ ] Для большинства контейнеров (`Card`, `Grid`, `Panel`, `div` и т.д.) дочерние компоненты описываются в массиве
  `children`.
- [ ] Для компонентов типа `Accordion`, `Tabs` основной контент (панели/вкладки) описывается в массиве `items`. Каждый
  элемент `items` должен содержать `props.header` и `children` для контента панели/вкладки.
- [ ] Каждый дочерний элемент в `children` или `items` должен быть валидным JSON UI компонентом (со своим `type`,
  `props` и т.д.).

### 3.4. `model` (Для VModel компонентов)

- [ ] Используется для компонентов, взаимодействующих с `FormManager` (например, `inputtext`, `select`, `checkbox`).
- [ ] Должен содержать `form` (String, имя формы) и `field` (String, имя поля в форме).
- [ ] Для `select` и подобных компонентов, если опции загружаются динамически, `model.options` должен содержать
  `{ "action": "include", "type": "operation", "source": "адрес/в/datahub" }`.

### 3.5. `customHooks` (Клиентские действия)

- [ ] Определяет клиентские действия, обрабатываемые `hub.actionManager` на фронтенде.
- [ ] Ключи объекта – имена событий PrimeVue или стандартных DOM-событий (например, `click`, `change`).
- [ ] Значения – массив объектов действий. Каждое действие: `{ "action": "имяДействия", "data": { ... } }`.
- [ ] Имена действий (`navigateTo`, `sendData`, `confirm`, `closeDialog` и т.д.) должны быть из списка поддерживаемых
  `ActionManager`.
- [ ] Для `sendData`:
    - [ ] Убедиться, что указан `sendTo` (имя серверного действия в `actions/`) или `action` (аналогично `sendTo`). Это
      инициирует клиент-серверное взаимодействие, отправляя данные на бэкенд, где `App::moduleActions` обрабатывает
      запрос и вызывает соответствующий JSON-файл инструкции из `actions/`.
    - [ ] Если отправляется форма, указать `form: "имяФормы"`. Данные формы будут собраны и отправлены в `input!` буфер
      `DataHub`.
    - [ ] Если результат должен обновить данные в `StateManager/hub`, указать `target: "ключВHub"`.
- [ ] Для `confirm`: в `data.accept` может быть вложено другое действие (например, `sendData`).
- [ ] Пройдены ручные тесты по основным пользовательским сценариям.

### 3.6. `dialogConfig` (Для кнопок, открывающих диалоги)

- [ ] Если используется `dialogConfig` у компонента `Button`:
    - [ ] `dialogConfig.type` должен быть `"Dialog"`.
    - [ ] `dialogConfig.fields` должен быть массивом валидных JSON UI компонентов (инпутов для формы диалога), каждый со
      своим `model`, привязанным к форме диалога (например, `model: { form: "dialogForm", ... }`

## 14. Валидация определений пользовательских UI-компонентов (в `ui/layouts/`, `ui/sections/`)

Файлы, определяющие кастомные секции или лейауты UI (обычно в `implement-modules/<module>/<version>/ui/layouts/` или
`implement-modules/<module>/<version>/ui/sections/`), должны следовать этим правилам для успешной валидации:

- [ ] **Корневой `type`**: Должен быть стандартным HTML-тегом (например, `"type": "div"`) или валидным контейнерным
  компонентом PrimeVue. Использование имени самого файла компонента в качестве типа (например,
  `type: "qtu-dialog-layout"` для `qtu-dialog-layout.json`) приводит к ошибке "Unknown component type".
- [ ] **Отсутствие `propsSchema`**: Свойство `propsSchema` на корневом уровне определения пользовательского
  UI-компонента не поддерживается валидатором и должно быть удалено.
- [ ] **Структура `children`**: Специализированные свойства вроде `slots` или `template.children` (которые могли
  использоваться в более ранних версиях или внутренних концепциях) должны быть преобразованы в стандартный массив
  `children` для корневого элемента этого файла.
- [ ] **Упрощение внутреннего содержимого**: Любые нестандартные или сложные компоненты, используемые внутри этих
  определений (например, кастомный `Repeater`, `MarkdownView`), должны быть заменены на базовые HTML-теги, стандартные
  компоненты PrimeVue или статические примеры их использования. Это необходимо, так как валидатор может не знать о
  кастомных компонентах, которые не зарегистрированы глобально или не имеют своих схем валидации.
- [ ] **Отсутствие неподдерживаемых корневых свойств**: Свойства, такие как `condition` или `customHooks`, на корневом
  уровне файла определения пользовательского UI-компонента (если только этот файл не определяет *экземпляр* компонента
  PrimeVue, который их поддерживает) приводят к ошибкам "Unknown key" и должны быть удалены или их логика должна быть
  реализована другими способами.
- [ ] **Проверка стандартных ключей**: Убедиться, что все ключи в таких файлах (`name`, `props`, `children`, etc.)
  соответствуют ожиданиям валидатора для базового типа, указанного в `type`.

## Дополнительные замечания по разработке и отладке

- **Ограничения инструментов**: Стандартные инструменты разработки (например, функция `read_file` в AI-ассистенте) могут
  иметь ограничения при работе с очень большими JSON-файлами (например, обрезка содержимого). Это может существенно
  затруднять анализ, рефакторинг и отладку таких файлов.
- **Параметр `batch` в Actions**: Ключ `batch` (например, в действии `update`) используется для группировки нескольких
  операций. Хотя это валидный способ, в некоторых сложных случаях или для упрощения отладки может быть целесообразно "
  развернуть" пакетные операции в последовательность отдельных инструкций.
