# Руководство по Оптимизации и Стандартизации Внутримодульной Документации (согласно STD-MOD-DOC-001)

> **Кратко:** Этот гайд описывает процесс приведения документации внутри существующих и новых модулей в соответствие со
> стандартом, определенным в задаче `STD-MOD-DOC-001.json`. Цель — обеспечить единообразную, легко находимую и правильно
> версионируемую документацию для всех модулей системы.

## 1. Введение и Цели Оптимизации

Данная оптимизация направлена на реализацию стандарта документирования модулей, разработанного в рамках задачи
`[STD-MOD-DOC-001.json](mdc:script/engine/task_definitions/STD-MOD-DOC-001.json)`. Основные цели:

- **Единообразие**: Все модули должны следовать единой структуре и формату документации.
- **Двухуровневая структура**: Четкое разделение на глобальную (общую для модуля) и версионную (специфичную для версии
  `v*`) документацию.
- **Версионирование**: Документация, относящаяся к конкретной версии модуля, должна версионироваться вместе с кодом этой
  версии.
- **Обнаруживаемость**: Пользователи и разработчики должны легко находить необходимую документацию.
- **Поддержка**: Стандартизированная документация проще в поддержке и обновлении.

Ожидается, что итоговый стандарт будет размещен в `script/data/standards/module-documentation-standard.json` (или
аналогичном пути, указанном в `STD-MOD-DOC-001.json`). Этот гайд является практическим руководством по его внедрению.

## 2. Обзор Стандарта (на основе `STD-MOD-DOC-001.json`)

Перед началом работ необходимо ознакомиться с полным текстом задачи
`[STD-MOD-DOC-001.json](mdc:script/engine/task_definitions/STD-MOD-DOC-001.json)` и разрабатываемым на ее основе
стандартом. Ключевые аспекты стандарта включают:

### Уровень 1: Глобальная Документация Модуля

- **Расположение**: В корневой директории модуля (`implement-modules/<имя-модуля>/`).
- **Содержание**: Общая информация о модуле, его назначение, архитектура, правила контрибьюции, не привязанные к
  конкретной версии.
- **Обязательные файлы (пример)**:
    - `README.md`: Краткое описание модуля.
- **Рекомендуемая структура (пример)**:
    - `docs/`: Поддиректория для более объемных документов (например, `architecture.md`, `setup-guide.md`).

### Уровень 2: Версионная Документация Модуля

- **Расположение**: Внутри директории конкретной версии модуля (`implement-modules/<имя-модуля>/vX/`).
- **Содержание**: Информация, специфичная для данной версии: изменения, API, детали реализации, инструкции по
  использованию именно этой версии.
- **Обязательные файлы (пример)**:
    - `README.md`: Описание этой версии, ключевые отличия от предыдущей (если есть).
- **Рекомендуемая структура (пример)**:
    - `docs/`: Поддиректория для детальной технической документации версии (например, `api-vX.md`, `data-model-vX.md`).

### Общие Аспекты Стандарта:

- **Формат**: Преимущественно Markdown (`.md`).
- **Именование файлов**: Единообразное и понятное.
- **Регистрация и Связывание**: Механизмы учета файлов документации (например, через `_i/files-by-block.json`,
  `linkedFiles` в определениях задач, метаданные модуля).

## 3. Процесс Оптимизации и Стандартизации (Чек-лист)

Следующий чек-лист поможет провести оптимизацию документации в соответствии с новым стандартом.

### Шаг 1: Подготовка и Анализ

- [ ] **Изучить стандарт**: Полностью ознакомиться с финальной версией стандарта `module-documentation-standard.json` (
  путь будет определен по итогам `STD-MOD-DOC-001.json`).
- [ ] **Определить список модулей**: Составить список всех модулей в `implement-modules/` требующих стандартизации.
    - *Инструмент*: `pwsh -File ./main-index.ps1 -Mode ListDir -Path implement-modules` (или аналогичный).
- [ ] **Провести аудит существующей документации**: Для каждого модуля оценить текущее состояние документации:
    - [ ] Наличие и расположение глобальных файлов документации.
    - [ ] Наличие и расположение версионных файлов документации.
    - [ ] Соответствие текущей документации (если есть) основным принципам нового стандарта.

### Шаг 2: Внедрение Глобальной Документации Модуля

Для каждого модуля в `implement-modules/`:

- [ ] **Создать/обновить `README.md` в корне модуля**:
    - Должен содержать: краткое описание модуля, его основное назначение, статус.
- [ ] **Создать/организовать директорию `docs/` в корне модуля** (если требуется для объемных документов):
    - Переместить/создать здесь общие архитектурные описания, руководства по настройке (не зависящие от версии), гайды
      для контрибьюторов.
    - Пример: `implement-modules/<имя-модуля>/docs/architecture-overview.md`.
- [ ] **Проверить отсутствие версионно-специфичной информации** в глобальной документации.

### Шаг 3: Внедрение Версионной Документации Модуля

Для каждой директории `vX` внутри каждого модуля (`implement-modules/<имя-модуля>/vX/`):

- [ ] **Создать/обновить `README.md` в директории версии (`vX/README.md`)**:
    - Должен содержать: описание конкретной версии, список основных изменений по сравнению с предыдущей версией (если
      применимо), инструкции по использованию/установке этой версии.
- [ ] **Создать/организовать директорию `docs/` в директории версии (`vX/docs/`)** (если требуется):
    - Переместить/создать здесь детальную техническую документацию, специфичную для этой версии (например, описание API,
      модели данных, примеры кода).
    - Пример: `implement-modules/<имя-модуля>/v1/docs/api-reference.md`.
- [ ] **Убедиться, что документация отражает именно эту версию.**

### Шаг 4: Регистрация и Связывание Документации

- [ ] **Обновить метаданные модуля**: В соответствии с требованиями нового стандарта, обновить файлы
  `_i/files-by-block.json` или другие механизмы регистрации, чтобы они корректно отражали наличие и расположение файлов
  документации.
- [ ] **Обновить `linkedFiles`**: Если применимо, добавить пути к ключевым файлам документации в `linkedFiles`
  соответствующих определений задач (`task_definitions/`) или метаданных модуля.
- [ ] **Проверить доступность документации** через системные инструменты (если такие существуют, например, через
  `main-index.ps1` или UI).

### Шаг 5: Валидация и Контроль Качества

- [ ] **Разработать (или использовать существующие) правила валидации** для проверки соответствия документации
  стандарту (например, наличие обязательных файлов, корректная структура). Это может быть частью сценария
  `SCN-JsonModuleContinueTaskByValidator` или отдельный инструмент.
- [ ] **Провести выборочную проверку** нескольких модулей на полное соответствие стандарту.

### Шаг 6: Обновление Общих Руководств

- [ ] **Обновить `script/docs/start-session/true-module-fix.md`**: Добавить ссылки на новый стандарт документации и
  требования по его соблюдению при исправлении модулей.
- [ ] **Обновить другие релевантные гайды** (например, по созданию модулей), чтобы они отражали новый стандарт.

## 4. Принципы и Рекомендации

- **Итеративность**: Внедрение стандарта может быть итеративным процессом, особенно для большого количества модулей.
  Начните с наиболее критичных.
- **Автоматизация**: По возможности, автоматизируйте проверку соответствия стандарту (например, через скрипты или CI/CD
  пайплайны).
- **Примеры**: Создайте несколько "эталонно" документированных модулей, которые могут служить примером для остальных.
- **Обратная связь**: Собирайте обратную связь от разработчиков по удобству и полноте стандарта и этого руководства, при
  необходимости вносите улучшения.
