# Core Optimization: Руководство по Уменьшению Количества Хелперов (GENERIC-REDUCE-HELPERS-001)

> **Кратко:** Этот гайд — о том, как провести рефакторинг и оптимизацию вспомогательных файлов в директории
`app/Helpers/` с целью сокращения их общего количества, улучшения организации кода и уменьшения дублирования, в
> соответствии с задачей `GENERIC-REDUCE-HELPERS-001.json`. Основной фокус — на безопасном рефакторинге, сохранении
> функциональности и улучшении поддерживаемости ядра системы.

## Цели Задачи ([GENERIC-REDUCE-HELPERS-001.json](mdc:script/engine/task_definitions/GENERIC-REDUCE-HELPERS-001.json))

* **Анализ:** Изучить содержимое `app/Helpers/` и ее поддиректорий.
* **Выявление:** Найти дублирующиеся, избыточные или тесно связанные функции и классы в различных хелперах.
* **Планирование:** Определить:
    * Группы хелперов, которые можно логически объединить.
    * Отдельные файлы или функции для безопасного удаления (если не используются или их функциональность покрыта другими
      средствами).
    * Функции/классы для рефакторинга с целью улучшения их структуры или переноса в более подходящие места.
* **Реализация:** Внести изменения в кодовую базу PHP.
* **Обновление Использования:** Модифицировать все участки кода, которые использовали измененные или удаленные хелперы,
  чтобы они корректно работали с новой структурой.
* **Тестирование:** Убедиться в отсутствии регрессий и ошибок после рефакторинга.
* **Итог:** Уменьшенное количество файлов в `app/Helpers/`, консолидированная функциональность, улучшенная организация
  кода.

## Принципы Оптимизации Хелперов

1. **Безопасность Превыше Всего**: Основной приоритет — не нарушить существующую функциональность. Любое изменение
   должно быть тщательно протестировано.
2. **Улучшение Читаемости и Поддерживаемости**: Конечная цель — сделать код более понятным, логичным и легким для
   дальнейшей работы.
3. **Логическая Группировка**: Функции и классы должны быть сгруппированы по их доменной области или назначению, а не
   просто свалены в один большой файл.
4. **Устранение Дублирования (DRY)**: Активно выявлять и устранять повторяющиеся участки кода.
5. **Осторожное Удаление**: Удалять файлы или функции можно только после полной уверенности, что они не используются или
   их функциональность полностью покрыта и протестирована в другом месте. Используйте глобальный поиск по проекту.
6. **Следование Стандартам Кодирования**: Придерживаться существующих стандартов кодирования проекта (PSR, именование,
   комментирование).
7. **Атомарные Коммиты**: Фиксировать изменения небольшими, логически завершенными коммитами с понятными сообщениями.

## Что нельзя делать при оптимизации хелперов

* **Нельзя** менять публичные API существующих хелперов без крайней необходимости и без обновления всех мест их
  использования. Если сигнатура метода меняется, это должно быть осознанным решением.
* **Нельзя** удалять хелперы или их части, если есть хоть малейшее сомнение в том, что они где-то используются.
  Сначала — доказать неиспользование.
* **Нельзя** проводить рефакторинг без последующего тщательного тестирования.
* **Нельзя** объединять хелперы механически, не учитывая их логическую связь. Создание "мусорных" хелперов, содержащих
  все подряд, — это антипаттерн.
* **Нельзя** игнорировать существующие юнит-тесты. Если они есть, они должны проходить. Если их нет для изменяемого
  кода — это повод задуматься о их написании.
* **Нельзя** вносить изменения, не связанные напрямую с задачей уменьшения количества и улучшения организации хелперов (
  например, рефакторинг бизнес-логики в контроллерах, который просто использует хелпер).

## Как надо делать (алгоритм)

1. **Scan (Глубокий Анализ `app/Helpers/`)**
    * **Инвентаризация:** Составить список всех файлов в `app/Helpers/` и ее поддиректориях. Для каждого файла кратко
      описать его назначение и основные функции/классы.
    * **Анализ Зависимостей:** Определить, где и как используется каждый хелпер. Использовать инструменты IDE для поиска
      использований (`Find Usages`), а также глобальный текстовый поиск (`grep`, `rg`).
    * **Поиск Дублирования:** Искать схожие или идентичные функции/классы в разных файлах.
    * **Оценка Связности:** Определить, какие хелперы часто используются вместе или решают схожие задачи.
    * **Выявление "Мертвых" Хелперов:** Попытаться найти хелперы или их части, которые могут быть неиспользуемыми (
      кандидаты на удаление).
    * **Изучение Стандартов:** Просмотреть `script/docs/standards/` на предмет общих указаний по структуре кода, если
      применимо.

2. **Plan (Планирование Рефакторинга)**
    * **Определение Кандидатов на Объединение:** Сформировать группы хелперов, которые логично объединить в один файл.
      Дать новому объединенному хелперу понятное имя.
    * **Определение Кандидатов на Удаление/Рефакторинг:** Составить список хелперов/функций для удаления или для более
      глубокого рефакторинга (например, перенос метода в другой класс, изменение реализации).
    * **Определение Порядка Действий:** Решить, с каких хелперов начать. Возможно, стоит начать с самых очевидных
      кандидатов или с тех, у которых меньше зависимостей.
    * **План Обновления Зависимостей:** Для каждого планируемого изменения продумать, где потребуется обновить код,
      использующий этот хелпер.
    * **Стратегия Тестирования:** Определить, как будут проверяться изменения (ручное тестирование ключевых сценариев,
      существующие автоматические тесты, написание новых тестов).

3. **Refine-LEARN (Итеративное Улучшение и Фиксация Опыта)**
    * **Реализация (Шаг за Шагом):**
        * Внести одно логическое изменение (например, объединить два хелпера, удалить один неиспользуемый метод).
        * Обновить все места использования.
        * Тщательно протестировать.
        * Закоммитить изменения с четким сообщением.
    * **Документирование Решений:** Если принимаются нетривиальные решения (например, почему именно так объединяются
      хелперы, или почему удаляется конкретная функция), кратко фиксировать это в описании коммита или во временном
      рабочем документе.
    * **Фиксация Опыта:** По завершении задачи или ее крупных этапов:
        * Обновить `docs/development/lessons-learned.md` или аналогичный документ, если были выявлены общие паттерны,
          сложности или удачные подходы при рефакторинге хелперов.
        * Если в ходе рефакторинга возникли идеи по улучшению стандартов кодирования или структуры проекта,
          зафиксировать их для дальнейшего обсуждения.

## Частые ловушки и решения

* **"Страх трогать старый код"**: Преодолевается тщательным анализом, пошаговыми изменениями и хорошим тестированием.
  Начинайте с малого.
* **Недооценка количества зависимостей**: `Find Usages` в IDE — ваш лучший друг. Проверяйте зависимости до, а не после
  изменения.
* **Попытка сделать всё сразу**: Приводит к большим, сложным для ревью и отладки изменениям. Делайте небольшие атомарные
  шаги.
* **Недостаточное тестирование**: Критично. Если нет автотестов, необходимо тщательное ручное тестирование всех
  затронутых сценариев.
* **Конфликты слияния (merge conflicts)**: Если над кодовой базой работает несколько человек, чаще синхронизируйтесь с
  основной веткой и делайте небольшие коммиты.
* **Потеря функциональности из-за неправильного рефакторинга**: Двойная проверка логики до и после. Если возможно,
  попросите коллегу сделать ревью изменений.
