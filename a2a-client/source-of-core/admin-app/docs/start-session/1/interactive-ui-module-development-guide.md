# Core Optimization Guide for Interactive UI Modules (Inspired by Task ModuleDevelopment-00017)

> **Кратко:** Этот гайд — о том, как подходить к оптимизации и развитию **основных (core) систем PHP и UI**, которые
> обеспечивают работу интерактивных элементов в модулях. В отличие от `true-module-fix.md`, который фокусируется на
> исправлении самих модулей, этот документ рассматривает, как улучшить ядро системы, опираясь на потребности, выявленные
> при разработке сложных модулей, таких как `landing-main-page/v3` (
> задача [ModuleDevelopment-00017](mdc:script/engine/task_definitions/ModuleDevelopment-00017.json)).

## 1. Введение: Зачем оптимизировать ядро?

При разработке модулей с богатым интерактивным UI, таких как `landing-main-page/v3` из
задачи [ModuleDevelopment-00017](mdc:script/engine/task_definitions/ModuleDevelopment-00017.json), мы часто сталкиваемся
с необходимостью:

- Открывать диалоговые окна (с статическим контентом или формами).
- Обрабатывать данные форм, особенно в контексте диалогов.
- Реализовывать кастомную навигацию (navigation hooks).
- Обеспечивать надежную связь между UI-событиями (`@click`) и серверными действиями (`actions`).

Если базовые механизмы ядра, отвечающие за эти функции, сложны в использовании, недостаточно производительны или
ограничены, это приводит к усложнению разработки модулей, появлению бойлерплейта и потенциальным проблемам.

**Цель этого гайда** — наметить направления для анализа и оптимизации соответствующих частей PHP-ядра и связанных
UI-конвенций, чтобы упростить и стандартизировать разработку интерактивных UI-компонентов в модулях.

**Ссылка на задачу-катализатор:
** [ModuleDevelopment-00017: Upgrade landing-main-page Module to v3 with Interactive Buttons](mdc:script/engine/task_definitions/ModuleDevelopment-00017.json)

## 2. Общие принципы оптимизации ядра

- **Упрощение API для модулей**: Интерфейсы, которые ядро предоставляет модулям (для определения диалогов, форм,
  навигации), должны быть интуитивно понятными и требовать минимум конфигурации для стандартных случаев.
- **Производительность**: Операции ядра (обработка действий, рендеринг компонентов, работа с DataHub) должны быть
  эффективными.
- **Надежность и Предсказуемость**: Поведение ядра должно быть хорошо документировано и предсказуемо.
- **Расширяемость**: Ядро должно позволять легко добавлять новые типы интеракций или кастомизировать существующие без
  модификации самого ядра (например, через систему плагинов, хуков или четко определенных интерфейсов).
- **Консистентность**: Паттерны для реализации схожих UI-интеракций должны быть единообразными.
- **Обратная совместимость**: По возможности, изменения в ядре не должны ломать существующие модули, либо должен быть
  четкий план миграции.
- **Документация**: Любые изменения или улучшения в ядре должны сопровождаться обновлением соответствующей
  документации ([server-actions-reference.md](/docs/ui/commands-and-operations/server-actions-reference.md), гайды по
  UI и т.д.).

## 3. Что нельзя делать (при оптимизации ядра)

- Вносить изменения без четкого понимания их влияния на существующие модули и систему в целом.
- Оптимизировать преждевременно или без конкретных данных о производительности.
- Создавать слишком абстрактные или универсальные решения, которые усложняют простые случаи.
- Забывать об обновлении документации и примеров.
- Ломать обратную совместимость без крайней необходимости и без плана миграции для модулей.

## 4. Ключевые области ядра для анализа и оптимизации (на примере ModuleDevelopment-00017)

Задача [ModuleDevelopment-00017](mdc:script/engine/task_definitions/ModuleDevelopment-00017.json) требует реализации
трех типов интерактивных кнопок:

1. Диалог со статическим контентом.
2. Диалог с формой.
3. Кастомный navigation hook.

Это указывает на следующие области ядра, требующие внимания:

### 4.1. Система управления диалоговыми окнами

* **Текущее состояние и потенциальные проблемы (гипотезы):**
    * Как модули определяют контент диалогов (статический, динамический из шаблона, из файла)?
    * Насколько гибок механизм передачи данных в диалог и получения результата из него?
    * Есть ли стандартный способ управления состоянием диалога (открыт/закрыт, загрузка) из серверных `actions` или
      клиентских `customHooks`?
    * Существуют ли разные подходы к реализации диалогов в разных модулях? Можно ли их унифицировать?
* **Цели оптимизации:**
    * Предоставить простой и декларативный способ определения диалогов в JSON-структуре страниц/секций.
    * Обеспечить легкую загрузку контента для диалога (например, из `template` или отдельного `page` JSON).
    * Стандартизировать обработку событий диалога (open, close, submit).
* **Предлагаемые действия/расследования:**
    * Проанализировать существующие реализации диалогов в эталонных модулях (например, `question-to-user/v5`,
      `primary-form/v1`).
    * Рассмотреть возможность введения специального UI-компонента типа `"DialogTriggerButton"` или стандартизированного
      `@click` действия для открытия диалогов.
    * Исследовать, как
      `StepResponse` ([docs-mirrors/app/AiRudeDepot/App/StepResponse/StepResponse.md](mdc:docs-mirrors/app/AiRudeDepot/App/StepResponse/StepResponse.md))
      используется для управления диалогами.
* **Ключевые файлы/классы ядра:**
    * `App\AiRudeDepot\Processors\DataProcessor.php` ([mdc:app/AiRudeDepot/Processors/DataProcessor.php]) (как он
      обрабатывает UI-структуры, которые могут содержать диалоги).
    * Клиентская часть UI рендеринга (Vue компоненты для диалогов, например, PrimeVue Dialog).
    * `server-actions-reference.md` ([/docs/ui/commands-and-operations/server-actions-reference.md]) на предмет
      наличия/отсутствия стандартных `actions` для управления диалогами.

### 4.2. Обработка форм в диалоговых окнах

* **Текущее состояние и потенциальные проблемы (гипотезы):**
    * Как данные форм, находящихся внутри диалогов, собираются и отправляются на сервер?
    * Как происходит валидация этих форм и отображение ошибок внутри диалога?
    * Насколько легко переиспользовать существующие механизмы форм (`type: "Form"`) внутри диалогов?
* **Цели оптимизации:**
    * Обеспечить бесшовную интеграцию стандартных форм (`type: "Form"`) внутрь диалогов.
    * Упростить процесс отправки данных формы из диалога и обновление UI диалога/родительской страницы по результатам.
* **Предлагаемые действия/расследования:**
    * Проанализировать, как `WalkForForms.php` ([mdc:app/AiRudeDepot/Processors/DataProcessor/Php/WalkForForms.php])
      работает с формами, и можно ли его логику легко применить к формам в диалогах.
    * Изучить, как `@click` обработчики на кнопках сабмита в диалогах передают данные серверным `actions`.
    * Оценить, нужны ли специальные `actions` или параметры в `StepResponse` для обработки форм в диалогах.
* **Ключевые файлы/классы ядра:**
    *
    `App\AiRudeDepot\Processors\DataProcessor\Php\WalkForForms.php` ([mdc:app/AiRudeDepot/Processors/DataProcessor/Php/WalkForForms.php])
    *
    `App\AiRudeDepot\Processors\InstructionProcessor\StorageHelper.php` ([mdc:app/AiRudeDepot/Processors/InstructionProcessor/StorageHelper.php]) (
    обработка `actions`, которые получают данные от форм).
    * Компоненты форм (PrimeVue) и их интеграция.

### 4.3. Система Navigation Hooks (клиентская навигация)

* **Текущее состояние и потенциальные проблемы (гипотезы):**
    * Как определяются и регистрируются `customHooks` для навигации?
    * Насколько этот механизм стандартизирован и легко ли его использовать в модулях?
    * Как передаются параметры при такой навигации?
* **Цели оптимизации:**
    * Предоставить декларативный способ определения навигационных действий в JSON UI.
    * Обеспечить простой способ вызова навигации как из `@click` обработчиков, так и потенциально из серверных
      `actions` (через `output:commands` в `StepResponse`).
* **Предлагаемые действия/расследования:**
    * Проанализировать существующие `customHooks` и примеры их использования для навигации.
    * Рассмотреть, можно ли унифицировать вызовы навигации (например, через стандартное имя хука с параметрами).
    * Изучить возможности Inertia.js для управления клиентской навигацией и как это интегрировано.
* **Ключевые файлы/классы ядра:**
    * Место регистрации и выполнения `customHooks` (вероятно, в клиентском JS коде).
    * Документация по `customHooks` (если существует).
    *
    `StepResponse` ([docs-mirrors/app/AiRudeDepot/App/StepResponse/StepResponse.md](mdc:docs-mirrors/app/AiRudeDepot/App/StepResponse/StepResponse.md))
    и поле `output:redirect` или `output:commands` для управления навигацией с сервера.

### 4.4. Обработка UI-событий (`@click`) и вызов серверных Actions

* **Текущее состояние и потенциальные проблемы (гипотезы):**
    * Насколько гибок текущий механизм `@click` для вызова как клиентских хуков, так и серверных `actions`?
    * Как передаются параметры в `actions` из `@click`?
    * Как обрабатываются результаты выполнения `actions` и обновляется UI?
* **Цели оптимизации:**
    * Упростить синтаксис определения `@click` обработчиков.
    * Стандартизировать передачу параметров (например, из `formState`, `pageState` или атрибутов элемента).
    * Обеспечить четкую связь между `action` и обновлением конкретных частей UI (например, через `outputVariable` или
      более гранулярное обновление через `StepResponse`).
* **Предлагаемые действия/расследования:**
    * Проанализировать структуру `props: {"@click": ...}` в UI JSON и как она транслируется в вызовы.
    * Изучить, как `App.php` ([mdc:app/AiRudeDepot/App/App.php]) (или аналогичный обработчик POST-запросов)
      диспетчеризует вызовы `actions`.
    * Оценить, как `InstructionProcessor.php` ([mdc:app/AiRudeDepot/Processors/InstructionProcessor.php]) выполняет
      `actions` и формирует `StepResponse`.
* **Ключевые файлы/классы ядра:**
    * `App\AiRudeDepot\App\App.php` ([mdc:app/AiRudeDepot/App/App.php]) (или аналогичный) - точка входа для
      POST-запросов от UI.
    * `App\AiRudeDepot\Processors\InstructionProcessor.php` ([mdc:app/AiRudeDepot/Processors/InstructionProcessor.php])
    *
    `App\AiRudeDepot\Processors\InstructionProcessor\StorageHelper.php` ([mdc:app/AiRudeDepot/Processors/InstructionProcessor/StorageHelper.php])
    * `server-actions-reference.md` ([/docs/ui/commands-and-operations/server-actions-reference.md])

### 4.5. Совместимость версий модулей и эволюция ядра

* **Текущее состояние и потенциальные проблемы (гипотезы):**
    * Если ядро изменяется (например, меняется API для диалогов), как это повлияет на старые версии модулей, которые
      использовали старый API?
    * Существует ли механизм версионирования для API ядра или конвенции для обеспечения обратной совместимости?
* **Цели оптимизации:**
    * Минимизировать поломки старых модулей при обновлении ядра.
    * Предоставить четкие инструкции по миграции для разработчиков модулей, если изменения в ядре неизбежны.
* **Предлагаемые действия/расследования:**
    * При планировании изменений в ядре всегда учитывать их влияние на существующие модули.
    * Рассмотреть стратегии (например, адаптеры, временная поддержка старого API) для обеспечения более плавной
      миграции.
    * Улучшить документацию по версиям ядра и изменениям API.
* **Ключевые файлы/классы ядра:**
    * Все вышеперечисленные, а также общие конфигурационные файлы системы.

## 5. Процесс оптимизации ядра ("Scan-Plan-Refine-LEARN" для ядра)

1. **Scan (Сканирование и анализ):**
    * Изучить текущую реализацию функциональности в ядре (PHP классы, JS код).
    * Проанализировать, как эта функциональность используется в существующих модулях (особенно в эталонных и
      проблемных).
    * Собрать обратную связь от разработчиков модулей о болевых точках.
    * Использовать задачи,
      подобные [ModuleDevelopment-00017](mdc:script/engine/task_definitions/ModuleDevelopment-00017.json), как
      индикаторы областей, требующих улучшения.
2. **Plan (Планирование изменений):**
    * Сформулировать конкретные цели оптимизации для каждой области.
    * Предложить изменения в API, структуре кода или логике работы ядра.
    * Оценить влияние изменений на существующие модули и производительность.
    * Разработать план тестирования.
    * Запланировать обновление документации.
3. **Refine & Implement (Реализация и Уточнение):**
    * Реализовать запланированные изменения в ядре.
    * Провести тщательное тестирование (модульное, интеграционное).
    * При необходимости адаптировать несколько ключевых модулей под новый API в качестве пилотного проекта.
    * Уточнить реализацию на основе результатов тестирования и пилотного внедрения.
4. **LEARN & Document (Фиксация знаний и Документирование):**
    * Обновить всю релевантную документацию
      ядра ([server-actions-reference.md](/docs/ui/commands-and-operations/server-actions-reference.md), гайды,
      примеры).
    * Обновить или создать `lessons-learned.md` для разработчиков модулей, объясняющие, как использовать новые или
      улучшенные функции ядра.
    * Распространить информацию об изменениях среди команды разработчиков.
