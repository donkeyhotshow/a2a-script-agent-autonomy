**Ключевые моменты из `known-issues.md`:**

- **Критическая проблема: Нестабильная работа адресации `session!` и `model!`**:
    - Это основная причина ненадежности модуля.

    - Сохранение в `session:user` не всегда гарантирует доступность.
    - **Временное решение**: Дублирование данных сессии в `localStorage` и кэширование результатов запросов к модели
      также в `localStorage`. Приведены примеры JS-функций `storeUserSession`, `restoreSessionFromLocalStorage`,
      `getUserByCredentials`.
    - Это указывает на то, что значительная часть логики по работе с сессиями и данными может выполняться на клиенте (в
      JS) из-за проблем с серверными механизмами `session!` и `model!`.
- **Функциональные ограничения**:
    - **Нефункциональная социальная авторизация**: Из-за изменений в API соц. сетей. Рекомендация: использовать Laravel
      Socialite.
    - **Ограничения валидации**: Только базовая клиентская валидация. Нет полноценной валидации паролей, асинхронной
      валидации. Рекомендация: дополнять серверной валидацией.
    - **Проблемы с восстановлением пароля**: Требует настройки отправки email через Laravel, шаблоны email не включены,
      время жизни токена не настраивается.
- **Проблемы стилизации и адаптации**:
    - **Ограниченная кастомизация UI**: Глубокая кастомизация требует изменения исходных JSON. Стили жестко
      закодированы.
    - **Приоритеты CSS**: Указан порядок: Vue Flow > PrimeVue > Tailwind CSS. Это важно для понимания, как применяются и
      переопределяются стили.

**Lessons-learned (очень важные):**

* **Проблемы с `session!` и `model!`**: Это фундаментальная проблема, влияющая на архитектуру. Обходные пути через
  `localStorage` означают, что PHP-процессоры могут не полностью контролировать состояние, и часть логики перенесена на
  клиент. Понимание этого критично.
* **Клиентская логика (JS)**: Судя по примерам функций, в системе используется JS (`hub.sessionManager.set`,
  `localStorage.setItem`) для управления состоянием и данными, вероятно, в связке с JSON-определениями UI и
  actions/commands. `hub` - это, видимо, некий глобальный JS объект/библиотека.

`DataProcessor.php` — это действительно центральный движок для обработки данных и выполнения различных "модификаторов" (
как PHP-классов, так и JSON-инструкций).

**Ключевые моменты из `DataProcessor.php` (первая часть):**

- **Назначение**: Обрабатывает данные, применяя к ним "модификаторы". Модификаторы могут быть:
    - **PHP-классы**: Находятся в `App\AiRudeDepot\Processors\DataProcessor\Php\`. Имя класса формируется из имени
      вызываемого метода (например, `walkForOperations` -> `WalkForOperations.php`). Должны иметь статический метод
      `process(&$data, DataHub $commonStorage, ...$arguments)`.
    - **JSON-инструкции**: Файлы `.json` в `app/AiRudeDepot/Processors/DataProcessor/Json/`. Содержат массив
      инструкций (ключ `instructions` или инструкции в корне).
- **Конструктор `__construct($data = null, DataHub $commonStorage, StepResponse $response)`**:
    - Принимает начальные данные (`$data`), `DataHub` (для доступа к файлам/буферам) и `StepResponse`.
- **Статический метод `data($data, DataHub $commonStorage)`**: Фабричный метод для создания экземпляра `DataProcessor`.
- **Метод `__call($name, $arguments)`**: "Магический" метод, который вызывается, когда обращаются к несуществующему
  методу экземпляра (например, `$dataProcessor->walkForOperations(...)`).
    - `$name` становится именем модификатора.
    - **Логика выбора модификатора**:
        1. Ищет PHP-класс `\App\AiRudeDepot\Processors\DataProcessor\Php\{StudlyName}`. Если найден и имеет метод
           `process`, вызывает его.
        2. Если PHP-класс не найден, ищет JSON-файл `app/AiRudeDepot/Processors/DataProcessor/Json/{name}.json`. Если
           найден, загружает его и выполняет инструкции через `runJson()`.
    - **Работа с данными**:
        - Для PHP-модификаторов данные передаются по ссылке (`&$this->data`) и могут быть изменены напрямую, либо
          модификатор может вернуть новые данные.
        - Для JSON-модификаторов результат выполнения инструкций ожидается в буфере `output` (
          `$this->commonStorage->address('output')->get()`), который затем становится текущими данными процессора (
          `$this->data`).
    - Возвращает `$this` для возможности цепочки вызовов (fluent interface).
- **Метод `runJson($instructions, $arguments = [])`**:
    - Принимает массив инструкций или путь к JSON-файлу с инструкциями.
    - Аргументы (`$arguments`) помещаются в буфер `args` (`$this->commonStorage->address('args')->set(...)`).
    - Текущие данные процессора (`$this->data`) помещаются в буфер `input` (и, возможно, `output` как начальное
      значение).
    - Далее (в невидимой части файла) должен быть вызов `InstructionProcessor` для выполнения этих инструкций.
- **`StorageHelper` трейт**: Используется (вероятно, для `initializeActionHandlers()` и других утилит по работе с
  `DataHub`).
- **`$listForPhp`**: Статический массив с именами модификаторов, которые, вероятно, реализованы как PHP классы (
  `WalkForAssetUrls`, `WalkForForms`, `ExecuteInstructions`, `WalkForOperations`). Это подтверждает, что
  `walkForOperations` и `walkForForms` — это PHP-модификаторы.
- **Буферы `DataHub`**: Активно используются:
    - `args`: для передачи аргументов в JSON-инструкции.
    - `input`, `output`: для передачи данных в/из JSON-инструкций.
    - `history`: в `StepResponse` для логирования.

**Lessons-learned:**

* **Два типа модификаторов**: PHP-классы (в `Processors/DataProcessor/Php/`) и JSON-инструкции (в

* **Соглашения по именованию модификаторов**: `walkForOperations` -> `Php/WalkForOperations.php` или

- **Метод `actionUpdate($instruction): StepResponse`** (не виден полностью, но начало есть):
    - Выполняет одну операцию обновления.
    - Получает данные из `from` через `handleSource`.
    - Записывает их в `to` (адрес в `DataHub`) с помощью `$this->commonStorage->address($to)->set($valueToSet)`.
    - Поддерживает `mode` (`replace`, `merge`, `merge-recursive`, `append`, `prepend`).
- **Другие обработчики (видны в структуре, но не в деталях в этой части)**:
    - `handleSave($instruction)`: Для `"action": "save"`. Вероятно, вызывает `$instructionProcessor->save()` (который мы
      видели в `InstructionProcessor.php`).
    - `handleRemove($instruction)`: Для `"action": "remove"`. Вероятно, вызывает `$instructionProcessor->remove()`.
    - `handleReturn($instruction)`: Для `"action": "return"`. Вероятно, устанавливает флаг `completed` в `StepResponse`
      и может помещать данные в `output` буфер.

**Итоговое понимание выполнения JSON-инструкций:**

1. **`DataProcessor`** получает JSON-файл (например, action-файл).
2. `DataProcessor::runJson` (или `processActionFile` -> `runJson`) подготавливает буферы `args` и `input` в `DataHub`.
3. `runJson` вызывает `StorageHelper::executeInstructions` с массивом инструкций.
4. `executeInstructions` итерирует по инструкциям, вызывая `StorageHelper::processInstruction` для каждой.
5. `processInstruction` определяет тип `action` и вызывает соответствующий метод-обработчик (например, `handleUpdate`,
   `processForLoop`, `handleSave` и т.д.) из `$this->actionHandlers`.
6. Каждый метод-обработчик:
    - Использует `handleSource` для получения данных (`from`, `value`).
    - Выполняет свою логику (например, `for` итерирует и рекурсивно вызывает `processInstruction`; `update` записывает
      данные в `DataHub` по адресу `to`; `save` и `remove`, вероятно, создают/используют `InstructionProcessor` для
      вызова `$dataHubLinkedObject->save() / remove()`).
    - Возвращает `StepResponse`.
7. `executeInstructions` собирает (мержит) `StepResponse` от каждой инструкции.
8. `DataProcessor` получает итоговый `StepResponse`. Если это был JSON-модификатор, он может взять результат из буфера
   `output`.

    - Вызывает `self::processNode($data, $dataHub)` для рекурсивной обработки.
    - Результат `processNode` записывается обратно в `$data`.
- **Статический рекурсивный метод `processNode($node, DataHub $dataHub, $depth = 0)`**:
    - Если `$node` не массив, возвращает его как есть.
    - **Обработка узлов операций**:
        - Если текущий `$node` — это массив и содержит `{"type": "operation", "action": "..."}`:
            - **`"action": "include"`**:
                - Требует `"source"` (адрес в `DataHub`).
                - Загружает данные из `source` через `$dataHub->address($source)->get()`.
                - Если указано `"is_json": true` и данные — строка, пытается декодировать JSON.
                - **Рекурсивно вызывает `self::processNode()` для загруженных данных (`$sourceData`).** Результат этой
                  рекурсии заменяет собой узел `include`.
            - **`"action": "add"`**:
                - Аналогично `include`, загружает данные из `"source"`.
                - Декодирует JSON, если это строка и имя файла заканчивается на `.json` или не имеет расширения.
                - **Рекурсивно вызывает `self::processNode()` для загруженных данных (`$sourceData`).**
                - Возвращает обработанные данные (обернутые в массив, если не массив), которые затем будут "внедрены" в
                  родительский массив (см. логику обработки дочерних узлов).
            - **`"action": "remove"`**:
                - Просто возвращает `null`. Это сигнал для родительского узла, что данный элемент нужно удалить.
            - **Другие `action`**: Если `action` неизвестен, узел операции обрабатывается как обычный массив (его
              дочерние элементы проходят `processNode`).

        - Итерирует по `$node as $key => $value`.
        - Для каждого `$value` рекурсивно вызывает `$processedValue = self::processNode($value, $dataHub, $depth + 1)`.
        - Если `$processedValue === null` (результат `"action": "remove"`), этот дочерний элемент пропускается (
          удаляется).

              `"action": "include"`, вернувший список), то элементы из `$processedValue` "внедряются" (flattening) в
              `$newNode`.

**API `BufferController` также соответствует ожиданиям для "модуля хранения".**

**Lessons-learned:**

* API "модулей хранения" подтверждено и для `BufferController`. Основные методы (`get`, `set`, `remove`, `save`)
  присутствуют, но `save()` для буфера — это no-op.
* Буферы (например, `input`, `output`, `args` в `DataHub`) управляются экземплярами `BufferController` и хранят данные в
  памяти на время выполнения запроса/сценария.
