Read file: implement-modules/login-form/v1/actions/login-form/login.json
This `implement-modules/login-form/v1/actions/login-form/login.json` file is quite interesting when cross-referenced with the `README.md` of `login-form/v1`.

It's an `Instructions` type, as expected. Here's a breakdown of its `instructions` array:

1.  `{"action": "print_r", "from": "input"}`: Debugging step to print the input data.
2.  `{"action": "print_r", "from": "args"}`: Debugging step to print arguments (if any were passed to this action sequence).
3.  `{"action": "call", "from": "login-form/commands/authenticate"}`:
    *   This is the crucial step. It calls `login-form/commands/authenticate`.
    *   The `README.md` for `login-form/v1` stated that the `commands/` directory contains "PHP-классы для серверной логики" (PHP classes for server-side logic).
    *   This implies that the `call` action here is likely invoking a PHP class or method rather than another JSON instruction file (though `call` *can* call other JSON files). The path format `login-form/commands/authenticate` doesn't have a `.json` extension, which further suggests it might be referencing something handled differently, possibly by a naming convention that maps to a PHP class/method.
4.  `{"action": "update", "condition": "buffer:authenticated", "batch": [...]}`:
    *   This instruction runs only if `buffer:authenticated` is true (presumably set by the preceding `call` to the PHP command).
    *   The `batch` then:
        *   Copies `buffer:authenticatedUser` to `session!user`. This attempts to use the `session!` DataHub prefix, which the README noted as problematic in v1.
        *   Sets a success message in `buffer:successMessage`.
5.  `{"action": "update", "from": "buffer", "to": "output"}`: Copies the entire buffer to the output, which will be returned to the client.

**Key Observation**: The core authentication logic seems to be delegated via `action: "call"` to `login-form/commands/authenticate`, which, according to the module's README, points to PHP code. This is a significant architectural point, showing that the system isn't purely reliant on JSON instructions for all backend logic; it can dispatch to custom PHP handlers.
