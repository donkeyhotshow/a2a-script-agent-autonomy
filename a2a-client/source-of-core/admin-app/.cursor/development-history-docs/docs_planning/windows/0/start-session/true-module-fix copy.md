# True Module Fix: превращение нерабочих модулей в рабочие

Здравствуйте. Эта сессия предназначена для постоянного дообучения системы исправления модулей.

**Ваша цель — не просто исправлять нерабочие модули, а на каждом шаге:**

- Сканировать примеры (эталонные и проблемные модули).
- Анализировать, что отличает рабочие модули от нерабочих.
- Фиксировать новые best practices, паттерны, ошибки и решения в отдельном changelog/lessons-learned.
- Обновлять стандарты, чек-листы, документацию по мере появления новых кейсов.
- Применять новые знания к следующим задачам и модулям.

**Цикл работы:**

1. Сканируй структуру, процессы, документацию, примеры (
   используй [mdc:implement-modules/primary-form/v2/], [mdc:implement-modules/landing-main-page/v2/], [/docs/guides/module/01-overview-creating-modules.md]
   и другие гайды).
2. Анализируй отличия, выявляй новые паттерны.
3. Фиксируй новые знания (в changelog, lessons-learned, расширяй гайды).
4. Исправляй модуль, применяя все актуальные best practices.
5. После каждого исправления — обновляй стандарты, чтобы следующий модуль был ещё лучше.

**Если встречаешь что-то новое — обязательно фиксируй и интегрируй в систему!**

**Веди changelog/lessons-learned прямо в процессе работы.**

**Главная цель — чтобы система и стандарты постоянно развивались, а не просто повторяли старые ошибки.**

## 1. Что такое нерабочий и рабочий модуль?

- **Нерабочий модуль** — модуль, который не проходит валидацию, не соответствует стандартам, содержит ошибки, не покрыт
  тестами, не документирован, не интегрирован в систему, имеет устаревшие или битые файлы.
- **Рабочий модуль** — модуль, который полностью валиден, стандартизирован, покрыт тестами, документирован, интегрирован
  и поддерживается.

---

## 2. Быстрый старт: как исправить нерабочий модуль

1. Найди нерабочий модуль (например, через known-issues.md, ошибки валидации, жалобы пользователей).
2. Запусти сценарий глубокой валидации:
    - `pwsh -File ./main-work.ps1 -Mode RunScenario -ScenarioId SCN-JsonModuleContinueTaskByValidator -TaskId <TaskId>`
    - Или artisan: `php artisan validate:module-json <moduleName>`
3. Составь чеклист всех проблем (known-issues.md, checklist, результаты сценария).
4. Исправь модуль по чеклисту: структура, код, тесты, документация, интеграция.
5. Проверь, что модуль теперь рабочий по всем стандартам (см. чек-лист ниже и гайды выше).
6. Зафиксируй изменения в changelog, lessons-learned, обнови индексы.

---

## 3. Признаки нерабочего модуля

- Ошибки при сборке, валидации или запуске сценариев.
- Отсутствие или неактуальность документации (README.md, known-issues.md).
- Нет или неактуальны тесты.
- Устаревшие зависимости, битые или неиспользуемые файлы.
- Неактуальные версии, отсутствие миграции.
- Не проходит сценарии интеграции или пользовательского тестирования.
- Не соответствует стандартам оформления, структуры, именования.

## 4. Пошаговый процесс превращения нерабочего модуля в рабочий

### 4.1. Анализ и диагностика

- Запусти сценарии валидации (SCN-JsonModuleContinueTaskByValidator, artisan validate:module-json).
- Проверь документацию, структуру, тесты, интеграцию.
- Составь полный список проблем (known-issues.md, checklist, результаты сценариев).

### 4.2. План исправления

- Для каждой проблемы — сформулируй задачу/чеклист.
- Определи, что нужно переписать, что доработать, что удалить.
- Используй шаблоны задач (например, JsonModuleDeepCheck.template.json).

### 4.3. Исправление

- Исправь структуру директорий и файлов (см. пример ниже и гайды).
- Приведи код, данные, тесты, документацию к стандарту.
- Проверь интеграцию с системой (индексы, сценарии, зависимости).

### 4.4. Валидация и тестирование

- Повтори все проверки (сценарии, artisan, тесты), пока модуль не станет рабочим.
- Проверь соответствие чек-листу (см. GenericModuleDevelopment_Checklist.md и гайды).

### 4.5. Документирование и интеграция

- Обнови README.md, known-issues.md, changelog, lessons-learned.
- Обнови индексы, интеграцию, сценарии.

### 4.6. Финальное ревью и закрытие

- Проверь, что модуль теперь полностью рабочий по чек-листу и гайдам.
- Закрой задачу, обнови индексы, задокументируй результат.

## 5. Пример структуры рабочего модуля

```
implement-modules/<module-name>/v2/
├── docs/
│   ├── README.md
│   ├── known-issues.md
│   ├── index.md
│   └── ...
├── actions/
├── commands/
├── templates/
├── code/
├── validations/
├── data/
├── pages/
├── state/
├── _i/
└── ...
```

- **README.md** — обзор, проблемы, миграция, структура.
- **known-issues.md** — список известных проблем.
- **index.md** — структура документации.
- **code.md** — структура кода.

---

## 6. Пример: до/после

**До:**

- known-issues.md содержит длинный список нерешённых проблем.
- README.md устарел или отсутствует.
- artisan validate:module-json выдаёт ошибки.
- Нет тестов, неактуальные файлы, не проходит сценарии.

**После:**

- known-issues.md пуст или содержит только актуальные мелкие замечания.
- README.md подробно описывает модуль, структуру, миграцию, ограничения.
- Все проверки и сценарии проходят без ошибок.
- Есть тесты, документация, интеграция, changelog.

## 7. Чек-лист для рабочего модуля (см. GenericModuleDevelopment_Checklist.md и гайды выше)

- Чёткая цель и идентификатор модуля.
- Сбор и анализ контекста (SCN-CollectModuleImprovementContext).
- Актуальная документация (README.md, known-issues.md, index.md).
- Соответствие стандартам (task-definition-standard.json, operational-principles.json, гайды).
- Корректная структура директорий и файлов.
- Покрытие тестами, успешное прохождение сценариев.
- Интеграция с системой, обновлённые индексы.
- Lessons learned и changelog.
