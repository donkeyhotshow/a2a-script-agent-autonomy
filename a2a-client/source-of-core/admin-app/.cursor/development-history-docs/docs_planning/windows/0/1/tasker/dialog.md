      обработку шаблонов, манипуляции данными. Используют стандартные действия (`update`, `save`, `call`, `for` и т.д.)

    * **PHP Helper (`code/ModuleName.php`):** Для сложной логики, серверного рендеринга, работы с БД.
2. **UI Updates (Template Processing Pattern - Preferred):** **Это важно!** Рекомендуемый способ обновления UI — это
   модификация JSON-файла шаблона (например, `question-to-user/templates/question-area.json`, который мы видели в

   команд на изменение UI клиенту.
3. **Вызов JSON Actions:** Подтверждается, что JSON-действия вызываются из UI (например, по клику кнопки) с помощью
   `sendData` хука, который указывает путь к файлу действия (например,
   `question-to-user/v1/actions/processQuestions.json`).
4. **Доступ к данным из UI:** JSON-действия получают данные, отправленные клиентом (через `sendData`), используя
   плейсхолдер `{input:fieldName}`.

**Часть 2: Обсуждение Сценария "Прямого Выполнения Указаний Задачи"**

Вы предложили идею сценария, который бы:

1. Читал шаги (`steps`) активной задачи.
2. Выполнял эти шаги.
3. Имел стандартные шаги "подготовки" (чтение документации, проверка индексов, сбор данных).
4. Имел стандартные шаги "финализации" (валидация целостности через `./main.ps1`).

Это очень интересная концепция **"Движка Выполнения Задач" (Task Execution Engine)**, реализованного как QTU-сценарий.

**Как это может работать:**

* **QTU-Сценарий "TaskExecutor":** Назовем его `SCN-TaskExecutor.scenario.json`.
* **Вход:** Активная задача (читается из `context/active_task.id`).
* **Шаги Сценария `SCN-TaskExecutor`:**
    1. **Подготовка (Preparation Steps):**
        * `(Action)`: Прочитать активную задачу (`Show-Active-Task.ps1` или чтение JSON) и сохранить ее данные в
          контекст сценария (например, `$context.activeTask`).
        * `(Action/Info)`: Проверить поле `linkedFiles` задачи. Для каждого файла типа "Standard" или "Doc" прочитать
          его (если возможно) и/или вывести пользователю информацию/ссылку с требованием ознакомиться (основываясь на
          `operational-principles.json`).
        * `(Action/Question)`: Выполнить проверку индексов (если есть скрипт). Если проверка неудачна или требует
          действий, спросить пользователя.
        * `(Action/Question)`: Выполнить сбор дополнительных данных по индексу (если есть скрипт и понятно, что
          собирать).
    2. **Цикл Выполнения Шагов Задачи (Task Steps Execution Loop):**
        * `(Decision)`: Проверить, есть ли еще шаги в `$context.activeTask.steps`. Если нет, перейти к финализации.
        * `(Info/Question/Action)`: **Вот тут сложность.** Как интерпретировать шаг из `$context.activeTask.steps`?
            * **Если шаги в задаче - это просто текст (как сейчас):** Сценарий может просто показать текст текущего шага
              пользователю (шаг `Info`) и спросить "Шаг выполнен?" (шаг `Question` типа `yes_no`). Это превращает
              сценарий в интерактивный чек-лист.
            * **Если шаги в задаче - это структурированные команды:** Мы могли бы изменить стандарт задачи, чтобы поле
              `steps` содержало не просто строки, а объекты с типом действия (например,
              `{ "type": "runScript", "path": "./script/...", "args": [...] }` или
              `{ "type": "askUser", "prompt": "...", "variable": "..." }`). Тогда сценарий `SCN-TaskExecutor` мог бы
              пытаться выполнить эти команды (через шаг `Action` с `command` типа `Invoke-Expression` или более
              безопасные аналоги). Это значительно усложняет стандарт задачи, но делает выполнение более
              автоматизированным.
        * `(Decision)`: Перейти к следующему шагу задачи.
    3. **Финализация (Finalization Steps):**
        * `(Action)`: Запустить `./main.ps1` для валидации. (`Note:` Мы пока не знаем точно, что делает `./main.ps1`,
          кроме отображения дешборда).
        * `(Info)`: Показать результат валидации.
        * `(Question)`: Спросить пользователя, можно ли считать задачу выполненной (обновить статус на
          `pending-validation` или `completed`).
        * `(Action)`: Обновить статус задачи (потребуется скрипт типа `Update-TaskStatus.ps1`).

**Преимущества такого сценария:**

* Стандартизирует "обвязку" выполнения любой задачи (подготовка, финализация).
* Может частично автоматизировать выполнение, если шаги в задаче будут структурированы.
* Обеспечивает следование принципам (чтение доков в начале, валидация в конце).

**Сложности:**

* Интерпретация и выполнение шагов задачи (`steps`) — самая сложная часть. Простой показ текста и вопрос "сделано?" —
  реализуемо. Автоматическое выполнение требует структурированных шагов в самой задаче.
* Требуются дополнительные скрипты (например, `Update-TaskStatus.ps1`, скрипты для проверки индексов и т.д.).

действие (`renderQuestionUI.json`) будет получать данные из вызывающего QTU-сценария.**

**Предложение:**
QTU-сценарий (в шаге `Action`) должен будет передать в вызываемое JSON-действие (`renderQuestionUI.json`) объект с
данными вопроса. Этот объект должен соответствовать структуре шага `Question` из `question-to-user-standard.json`.

**Пример вызова из QTU-сценария (гипотетический):**

Допустим, у нас есть шаг `Question` в QTU-сценарии с `stepId: AskUserName`. В контексте QTU (`$Context.QTU`) есть
переменная `$Context.QTU.CurrentStepData`, содержащая JSON-объект этого шага:

```json
// Содержимое $Context.QTU.CurrentStepData
{
  "stepId": "AskUserName",
  "type": "Question",
  "category": "UserInput",
  "description": "Ask for the user's name",
  "questionText": "Please enter your name:",
  "input": {
    "type": "string",
    "validationRegex": "^[A-Za-z]+$",
    "allowEmpty": false
  },
  "context": { "provides": ["userName"] },
  "transitions": [{ "condition": "default", "nextStepId": "ShowGreeting" }]
}
```

Шаг `Action` в QTU-сценарии, который должен вызвать рендеринг UI, мог бы выглядеть так:

```json
{
  "stepId": "RenderUserNameQuestion",
  "type": "Action",
  "category": "UI",
  "description": "Render the UI for asking the user name",
  "action": {
    // Нужен механизм вызова JSON-действия модуля
    // Вариант 1: Прямой вызов, если движок это поддерживает
    "command": "Invoke-ModuleJsonAction",
    "args": [
        "implement-modules/question-to-user/v1/actions/renderQuestionUI.json", // Путь к действию
        "{{Context.QTU.CurrentStepData}}" // Передаем данные шага Question
    ]
    // Вариант 2: Через запись во временный буфер/файл
    // "command": "Set-Content -Path temp/qtu_render_input.json -Value {{Context.QTU.CurrentStepData | ConvertTo-Json -Depth 5}}; Invoke-SomeTriggerMechanismForModule"
  },
  "onError": { "nextStepId": "ErrorRenderingUI" },
  "transitions": [{ "condition": "default", "nextStepId": "WaitForUserInput_UserName" }] // Переход к шагу ожидания ввода
}
```

**Что должно делать `renderQuestionUI.json` (наша цель рефакторинга):**

1. Получить на вход JSON-объект шага `Question` (как в примере `$Context.QTU.CurrentStepData`).
2. Извлечь из него `input.type` (в примере это "string").
3. Извлечь `questionText`, `input.validationRegex`, `stepId` (для привязки ответа) и т.д.
4. На основе `input.type` выбрать нужный шаблон из `data/blanks/` (например, `text_input.json`).
5. Заполнить шаблон этими данными.
6. Вставить результат в `templates/question-area.json`.
7. Сохранить `templates/question-area.json`.

Это определение интерфейса между QTU-сценарием и модулем QTU кажется логичным. "Другая сессия", выполняющая
`REF-QTU-MODULE-001`, должна будет реализовать `renderQuestionUI.json` в соответствии с этим и, возможно,
уточнить/реализовать механизм вызова JSON-действия модуля из QTU-сценария (часть `"command"` и `"args"` в примере шага
`Action` выше).
