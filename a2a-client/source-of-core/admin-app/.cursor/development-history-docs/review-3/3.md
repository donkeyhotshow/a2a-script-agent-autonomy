
# Углубленный анализ компонентов системы

## 10. Жизненный цикл задач и сценариев

### 10.1 Инициализация и активация задачи

1. **Создание задачи**:
   - Задача создается через `SCN-CreateTask` сценарий
   - Генерируется файл `.json` в `script/engine/task_definitions/`
   - Задаче присваивается уникальный ID и тип задачи

2. **Активация задачи**:
   - Сценарий `SCN-ActivateTask` устанавливает задачу как активную
   - Вызывает `set-active-task.ps1` для обновления системного состояния
   - Устанавливает статус задачи `InProgress`

3. **Сбор данных**:
   - `SCN-FullyCollectTaskData` собирает индексную информацию
   - Использует `SCN-IndexCollectTaskData` для поиска релевантных файлов
   - Результаты сохраняются в `taskIndexResults` или `collectedIndexData`

### 10.2 Выполнение сценария

1. **Прогресс сценария**:
   - Маркеры прогресса хранятся в `engine/markers/<ScenarioId>.<ContextIdentifier>.json`
   - Отслеживают `current_step_id`, `status` и накопленный `context`
   - Статусы: `InProgress`, `HaltedForInput`, `Completed`, `Error`

2. **Типы шагов**:
   - **Action**: Выполняет PowerShell скрипты или PHP действия
   - **Question**: Запрашивает ввод от пользователя и останавливает выполнение
   - **QueryIndex**: Выполняет поиск в индексе файлов
   - **End**: Завершает сценарий

3. **Контекст сценария**:
   - Ключевые переменные, такие как `taskId`, `projectRoot`, `userInputValue`
   - Результаты шагов автоматически объединяются в контекст
   - Контекст используется для шаблонизации последующих шагов

### 10.3 Закрытие задачи

1. **Проверка критериев приемки**:
   - Задачи имеют определенные `acceptanceCriteria` для выполнения
   - `SCN-CloseTask` проверяет выполнение критериев
   - Переводит задачу в статус `Completed`

2. **Автоматическая активация зависимостей**:
   - Задачи могут иметь зависимые задачи через `contextDependencies.requiredTasks`
   - При завершении задачи автоматически активируется следующая зависимая задача

## 11. JSON-UI: Углубленный взгляд

### 11.1 Архитектура Клиентского Фреймворка

1. **HubManager и StateManager**:
   - Центральный объект `hub` управляет состоянием приложения
   - Реализует паттерн Observer для обновления компонентов
   - Предоставляет доступ к данным через `hub.get(path)` и `hub.update(path, value)`

2. **Компонентная модель**:
   - **RenderJson**: Основная точка входа для рендеринга JSON компонентов
   - **Presets**: Преобразует JSON в Vue компоненты через маппинг категорий
   - **ComponentMap**: Конфигурирует маппинг между JSON типами и Vue компонентами

3. **Обработка событий**:
   - `customHooks` определяют действия на события компонентов
   - `ActionManager` обрабатывает действия: `sendData`, `navigateTo`, `alert`
   - `NotifyManager` реализует систему событий для межкомпонентной коммуникации

### 11.2 Техники Рендеринга JSON UI

1. **Многоуровневая трансформация**:
   - JSON определение → категория компонента → конкретный Vue компонент
   - Например: `{"type": "button"}` → `Component` → `Button.vue`

2. **Динамическое расширение**:
   - Поддержка `include` операций для композиции интерфейса
   - Разрешение переменных в атрибутах через плейсхолдеры `{path/to/data}`
   - Динамическая загрузка компонентов через `defineAsyncComponent`

3. **Управление формами**:
   - `FormManager` для состояния форм, валидации, статуса загрузки
   - Связывание через `model: { form: "formName", field: "fieldName" }`
   - Автоматическая подгрузка ошибок валидации из буфера `buffer:validationErrors`

## 12. DataHub: Центр системы данных

### 12.1 Модель адресации

1. **Синтаксис адресов**:
   - Префиксы типов хранилищ: `file!`, `buffer:`, `model!`, `session!`
   - Путь к ресурсу: `storagePath`
   - JSON-ключи: `:key1.key2...`
   - Query-параметры: `?param=value...`

2. **Разрешение адресов**:
   - Плейсхолдеры `{адрес_в_DataHub}` для динамических адресов
   - Рекурсивное разрешение вложенных плейсхолдеров
   - Максимальная глубина разрешения для избежания циклических ссылок

3. **Контроллеры данных**:
   - Каждый тип данных имеет специализированный контроллер
   - Единый программный интерфейс через `InstructionProcessor`
   - Спецификация операций в сегментах пути для `mysql!` и `model!`

### 12.2 Операции с данными

1. **CRUD операции**:
   - `get`: Получение данных из хранилища
   - `set`: Установка значения по адресу
   - `save`: Сохранение в постоянное хранилище
   - `remove`: Удаление данных
   - `find`: Поиск в данных по критериям

2. **Преобразования данных**:
   - `applyDataTransformation`: Преобразование данных через `with`
   - `searchInData`: Сложный поиск через `find`
   - `evaluateCondition`: Оценка условий для выполнения инструкций

3. **Управление буферами**:
   - Стандартные буферы: `input`, `output`, `args`
   - Контекстные буферы: `buffer:for.currentItem`, `buffer:for.currentIndex`
   - Сохранение результатов валидации в `buffer:validationErrors`

## 13. Оптимизация и масштабирование

### 13.1 Производительность системы

1. **Кэширование**:
   - Кэширование модульных экземпляров в DataHub
   - Буферизация данных в памяти для частых операций
   - Атомарная запись через временные файлы для надежности

2. **Индексация**:
   - `main-index.ps1` для быстрого поиска по метаданным
   - Оптимизированные индексные структуры для разных типов файлов
   - Инкрементальное обновление индексов для больших репозиториев

3. **Асинхронные операции**:
   - Использование `defineAsyncComponent` для ленивой загрузки компонентов
   - Фоновое выполнение долгих операций через PowerShell
   - Управление состоянием запросов через FormManager

### 13.2 Архитектурные паттерны

1. **Модульность и вертикальные срезы**:
   - Независимые модули с явными зависимостями
   - Вертикальная организация функциональности
   - Стандартизированные интерфейсы между модулями

2. **Обработка инструкций**:
   - Интерпретатор JSON-инструкций в StorageHelper
   - Чейнинг модификаторов в DataProcessor
   - Разделение управляющей и исполняющей логики

3. **Обработка событий**:
   - Интеграция Event Bus через NotifyManager
   - Декларативное определение обработчиков событий
   - Гранулярное обновление компонентов при изменении данных

## 14. Интеграция систем и расширение функциональности

### 14.1 Стратегии интеграции

1. **Модульное расширение**:
   - Создание новых модулей с использованием эталонных шаблонов
   - Интеграция через стандартные `_i/` механизмы
   - Отделение бизнес-логики от UI через JSON-шаблоны

2. **Сценарное управление**:
   - Создание новых сценариев для автоматизации процессов
   - Расширение существующих через добавление шагов
   - Интеграция внешних систем через PHP/PowerShell адаптеры

3. **Индексная интеграция**:
   - Добавление новых типов индексов для специфичных данных
   - Расширение схемы поиска через модификацию `index-processor.php`
   - Интеграция с внешними поисковыми системами

### 14.2 Методология разработки

1. **Стандарты и валидация**:
   - Строгое соответствие структурным стандартам
   - Использование валидаторов JSON структур
   - Сравнение с эталонными модулями

2. **Процесс Scan-Plan-Refine**:
   - Сканирование существующей кодовой базы
   - Планирование изменений на основе анализа
   - Уточнение и оптимизация реализации

3. **QTU система для решения проблем**:
   - Question-To-User (QTU) для сбора контекста
   - Структурированные формы вопросов
   - Интеграция ответов в рабочий процесс
