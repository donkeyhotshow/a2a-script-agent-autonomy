#### 1. Проблема с кодировкой Unicode (КРИТИЧНО) ✅ ИСПРАВЛЕНО
**Описание:** Команда с Unicode символами (кириллица, китайские иероглифы, эмодзи) возвращает искаженный вывод.

**Тестовая команда:**
```powershell
Write-Host "Unicode test: Привет 世界 🌍"
```

**Ожидаемый результат:**
```
Unicode test: Привет 世界 🌍
```

**Фактический результат (до исправления):**
```
Unicode test: ਢ ?? ??
```

**Код возврата:** 0 (команда выполнена успешно, но вывод искажен)

**Приоритет:** ВЫСОКИЙ

**Локация:** `lib/command-executor-wrapper.cjs`, `set-encoding.cjs`

**Решение:** Установка UTF-8 кодировки перед выполнением команды (см. раздел "Исправления")

**Варианты решения (ADR):**

1. **Жёсткая унификация на UTF‑8 «от конца до конца»**
   - Суть: Принять стратегию «везде UTF‑8» для MCP terminal: на стороне PowerShell явно выставлять `$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new($false)` и/или `chcp 65001`, на стороне Node‑обработчика MCP терминала — интерпретировать stdout/stderr как UTF‑8 без перекодирования.
   - Стоимость: Средняя: потребуется аккуратно обновить обёртку MCP terminal и, возможно, стартовый скрипт PowerShell, добавить/обновить документацию и несколько целевых тестов на кириллицу.
   - Польза: Предсказуемая кодировка во всех сценариях, упрощение обработки строк (особенно в тестах и логах), выравнивание с остальными частями экосистемы Node.
   - Риски: Возможные побочные эффекты для существующих скриптов/окружений, которые молча полагались на текущую OEM‑кодировку консоли Windows; требуется регрессионное тестирование и, желательно, feature‑флаг/конфиг для поэтапного включения.
   - **Выбрано:** ✅ Реализовано

2. **Локальный адаптер перекодировки в MCP terminal**
   - Суть: Сохранить текущую кодировку консоли PowerShell (например, OEM‑866/Windows‑1251), а в слое MCP terminal реализовать явный адаптер: читать stdout/stderr в «консольной» кодировке и перекодировать в UTF‑8 перед передачей в ассистента/клиента.
   - Стоимость: Средняя–высокая: нужно надёжно определить текущую кодировку (через PowerShell/`[Console]::OutputEncoding`), реализовать конвертер и покрыть его тестами на разных типах строк (ASCII, кириллица, смешанные).
   - Польза: Минимальное вмешательство в рабочее окружение PowerShell, меньше риска сломать существующие сценарии, при этом пользователь MCP terminal уже получает корректный UTF‑8.
   - Риски: Усложнение кода MCP terminal; риск расхождений, если кодировка консоли будет меняться динамически/пользовательскими настройками; необходимость поддержки/отладки специфики Windows‑кодировок.

3. **Ограниченный workaround + явное документирование ограничения**
   - Суть: Зафиксировать текущее поведение как известное ограничение: гарантировать корректность только ASCII/латиницы в пользовательском выводе MCP terminal, а кириллицу обрабатывать частично (например, через escape‑последовательности/hex‑вывод в диагностических сценариях).
   - Стоимость: Низкая: не требует немедленных изменений в коде MCP terminal, только документация и, при желании, вспомогательные утилиты для диагностики.
   - Польза: Нулевой риск для существующих сценариев, быстрый способ формально закрыть диагностику и двигаться дальше по другим задачам.
   - Риски: Ограничение UX и локализации: пользователю по‑прежнему неудобно читать кириллицу в выводе; проблема перекладывается на более поздний этап, остаётся техническим долгом, который может всплыть при развитии терминала.

#### 11. Блокировка команд без установленной рабочей директории ✅ ИСПРАВЛЕНО
**Описание:** Все команды PowerShell блокируются проверкой `sessionVars.hasProjectWorkspace()`, даже если команды технически выполняются. Вместо результатов команд возвращается только предупреждение о необходимости установить рабочую директорию.

**Локация:** `handlers/terminal-handler.cjs`, строки 831, 942

**Симптомы:**
- Все команды возвращают одинаковое сообщение: "Рабочая директория не установлена"
- Результаты выполнения команд не возвращаются
- Код возврата всегда `0` (OK), но фактический вывод команды отсутствует
- Предупреждение появляется даже для простых команд типа `Get-Location`, `Write-Output`, `Get-Date`

**Примеры проблемных команд:**
```powershell
Get-Location                    # Блокируется
Get-ChildItem -Force            # Блокируется
Get-Date -Format "yyyy-MM-dd"   # Блокируется
Write-Output "Test"             # Блокируется
$env:USERPROFILE               # Блокируется
Test-Path "package.json"       # Блокируется
```

**Корневая причина:**
Код проверяет `sessionVars.hasProjectWorkspace()` перед выполнением команды и возвращает предупреждение вместо выполнения. При этом:
1. Команды не выполняются (или выполняются, но их вывод не возвращается)
2. Нет способа установить workspace через обычные команды PowerShell
3. Предлагается использовать JSON-формат `{"action": "workspace", "subAction": "set"}`, но этот формат не работает через строковую команду

**Влияние:**
- **Критично:** Невозможно выполнить любые команды без предварительной установки workspace
- **Проблема UX:** Пользователь не может выполнить даже базовые команды для диагностики
- **Нарушение принципа:** Команды должны выполняться в текущей директории по умолчанию

**Решение:** ✅ Исправлено
- Добавлена автоматическая установка workspace из `resolvedCwd` в методах `handleTerminalTool` и `handleDirectTerminalCommand`
- Смягчена проверка `hasProjectWorkspace()`: команды разрешены, если есть `resolvedCwd` как fallback
- Улучшена обработка JSON-команд: распознавание структурированных действий (`action`, `subAction`) до передачи в PowerShell

**Результат:**
- Команды теперь выполняются без явной установки workspace, если есть `args.cwd` или `process.env.WORKSPACE_ROOT`
- JSON-команды типа `{"action": "workspace", "subAction": "set", "path": "..."}` корректно обрабатываются через `handleStructuredTerminalAction`
- Результаты команд возвращаются корректно

#### 12. Некорректная обработка JSON-команд для установки workspace ✅ ИСПРАВЛЕНО
**Описание:** Попытка установить workspace через JSON-команду приводит к ошибке парсинга PowerShell.

**Симптомы:**
```powershell
{"action": "workspace", "subAction": "set", "path": "C:\\apps\\root\\mcp\\node-terminal"}
# Результат: ParserError: Unexpected token ':' in expression or statement
```

**Корневая причина:**
JSON-команда передаётся как строка PowerShell, а не как структурированный объект. PowerShell пытается выполнить JSON как команду, что приводит к синтаксической ошибке.

**Ожидаемое поведение:**
MCP terminal должен распознавать JSON-команды и обрабатывать их как структурированные действия, а не как строковые команды PowerShell.

**Решение:** ✅ Исправлено
- JSON-команды теперь распознаются до передачи в PowerShell
- Обрабатываются через `handleStructuredTerminalAction`

**Воспроизведение:**
```powershell
mcp_node-terminal_terminal(command="cd ..; Get-Location; cd node-terminal; Get-Location", ...)
# Результат: Error: Directory 'C:\apps\root\mcp\node-terminal\..; Get-Location; cd node-terminal; Get-Location' does not exist
```

**Влияние:**
- Среднее: Может блокировать выполнение сложных команд с несколькими операциями
