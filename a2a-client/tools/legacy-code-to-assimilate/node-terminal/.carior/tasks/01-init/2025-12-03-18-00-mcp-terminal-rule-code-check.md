## Контекст
Правило `.cursor/rules/mcp-terminal-mandatory.mdc` требует:
1. Обертка должна инициализировать тулзы и проксировать их в MCP сервер
2. Когда MCP сервер не работает, обертка должна возвращать ошибку о недоступности тула
3. При получении ошибки о недоступности тула работа над задачей должна быть остановлена

## Технические ограничения

### Архитектурные ограничения

1. **Обертка не знает содержимое запросов**
   - Обертка работает на уровне потока данных (stdin/stdout), а не на уровне JSON-RPC протокола
   - Для перехвата запросов нужно парсить JSON-RPC сообщения, что усложняет обертку

2. **MCP клиент сам обнаруживает недоступность тула**
   - Когда сервер не работает, MCP клиент (Cursor) сам обнаружит, что тул недоступен, потому что не получит ответа на запрос `tools/list` или `tools/call`
   - Это стандартное поведение MCP протокола

3. **Таймауты на стороне клиента**
   - MCP клиент имеет свои таймауты для запросов
   - Если сервер не отвечает, клиент получит timeout и пометит тул как недоступный

## Рекомендации

### Вариант 1: Улучшить проверку состояния сервера (рекомендуется)

Добавить проверку состояния сервера перед проксированием запросов:

```javascript
// Простое проксирование stdin с проверкой состояния
process.stdin.on('data', (chunk) => {
  // Проверяем, что сервер работает
  if (!child || child.killed || wrapperState.state !== 'running') {
    // Сервер не работает - не проксируем запрос
    debugLog(`Server not available, state: ${wrapperState.state}`);
    return;
  }
  
  if (child.stdin && child.stdin.writable) {
    try {
      child.stdin.write(chunk);
    } catch (err) {
      if (err.code !== 'EPIPE') {
        debugLog(`stdin write error: ${err.message}`);
      }
    }
  }
});
```

**Преимущества:**
- Простая реализация
- Не требует парсинга JSON-RPC
- Предотвращает отправку запросов упавшему серверу

**Недостатки:**
- Не возвращает явную ошибку о недоступности тула
- Клиент все равно получит timeout

### Вариант 2: Парсинг JSON-RPC для перехвата запросов (сложнее)

Добавить парсинг JSON-RPC запросов и возврат ошибки о недоступности тула:

```javascript
// Парсинг stdin для перехвата запросов
let stdinBuffer = '';
process.stdin.on('data', (chunk) => {
  stdinBuffer += chunk.toString('utf8');
  
  // Разбиваем по строкам (JSON-RPC сообщения разделены \n)
  const lines = stdinBuffer.split(/\r?\n/);
  stdinBuffer = lines.pop() || '';
  
  for (const line of lines) {
    const trimmed = line.trim();
    if (trimmed && trimmed.startsWith('{') && trimmed.endsWith('}')) {
      try {
        const request = JSON.parse(trimmed);
        
        // Проверяем состояние сервера перед проксированием
        if (!child || child.killed || wrapperState.state !== 'running') {
          // Возвращаем ошибку о недоступности тула
          if (request.method === 'tools/call' || request.method === 'tools/list') {
            const errorResponse = {
              jsonrpc: '2.0',
              id: request.id,
              error: {
                code: -32603,
                message: 'Tool unavailable: MCP server is not responding',
                data: {
                  state: wrapperState.state,
                  reason: wrapperState.reason,
                  lastError: wrapperState.lastError
                }
              }
            };
            process.stdout.write(JSON.stringify(errorResponse) + '\n');
            continue;
          }
        }
        
        // Проксируем запрос, если сервер работает
        if (child && child.stdin && child.stdin.writable) {
          child.stdin.write(trimmed + '\n');
        }
      } catch (e) {
        // Не JSON - проксируем как есть
        if (child && child.stdin && child.stdin.writable) {
          child.stdin.write(trimmed + '\n');
        }
      }
    }
  }
});
```

**Преимущества:**
- Возвращает явную ошибку о недоступности тула
- Клиент сразу получает информацию о проблеме
- Соответствует требованию правила

**Недостатки:**
- Сложнее реализация
- Требует парсинга JSON-RPC
- Может быть избыточно, если клиент сам обнаруживает недоступность

### Вариант 1: Улучшение проверки состояния сервера (реализован)

**Изменения в `server-wrapper-simple.cjs`:**

1. **Удалена регистрация обработчика stdin из функции `startServer()`**
   - Обработчик больше не регистрируется при каждом перезапуске сервера
   - Предотвращает дублирование обработчиков

2. **Добавлен единый обработчик stdin с проверкой состояния**
   - Обработчик зарегистрирован один раз перед вызовом `startServer()`
   - Проверяет состояние сервера перед проксированием каждого запроса:
     - `!child` - процесс не существует
     - `child.killed` - процесс убит
     - `wrapperState.state !== 'running'` - сервер не в рабочем состоянии
   - Логирует ситуацию только для состояний, отличных от `restarting` и `initializing`

**Код реализации:**
```javascript
// Проксирование stdin с проверкой состояния сервера
// Регистрируем обработчик один раз, он будет проверять состояние при каждом запросе
process.stdin.on('data', (chunk) => {
  // Проверяем, что сервер работает перед проксированием запросов
  if (!child || child.killed || wrapperState.state !== 'running') {
    // Сервер не работает - не проксируем запрос
    // Логируем только если это не обычная ситуация (например, при перезапуске)
    if (wrapperState.state !== 'restarting' && wrapperState.state !== 'initializing') {
      debugLog(`Server not available, state: ${wrapperState.state}, skipping request`);
    }
    return;
  }
  
  // Сервер работает - проксируем запрос
  if (child.stdin && child.stdin.writable) {
    try {
      child.stdin.write(chunk);
    } catch (err) {
      if (err.code !== 'EPIPE') {
        debugLog(`stdin write error: ${err.message}`);
      }
    }
  }
});
```
