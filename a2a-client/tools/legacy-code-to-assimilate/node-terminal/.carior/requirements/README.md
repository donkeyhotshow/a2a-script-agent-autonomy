# Структура требований MCP Terminal Server

## 📋 Обзор

Этот каталог содержит модульную структуру требований для проекта MCP Terminal Server - enterprise-grade сервера для безопасного выполнения команд терминала через MCP (Model Context Protocol).

## 📂 Описание разделов

### Core Foundation (`core/`)
Основные требования к архитектуре, базовым классам, сервисам и конфигурации проекта.

**Файлы:**
- `requirements-core-foundation.md` - главный файл с summary, сводным списком файлов, захардкоженными местами

**Что внутри:**
- Архитектура проекта (модульная структура в `mcp/server/`)
- Базовые классы и интерфейсы (`mcp/server/core/ModuleBase.cjs`)
- Общие сервисы (`mcp/` - утилиты)
- Конфигурация и настройки
- Захардкоженные места
- Планы миграции на пакетную архитектуру (будущее)

**Что вне:**
- Детальные требования к терминалу (в `terminal/`)
- Требования безопасности (в `security/`)
- Тестовые требования (в `testing/`)

**Планы миграции (будущее):**
- Требования для будущей пакетной архитектуры: `packages/*/docs/requirements/` (планируется)

### Terminal (`terminal/`)
Требования к функциональности терминала - выполнение команд, управление рабочими директориями, история команд.

**Файлы:**
- `requirements-terminal.md` - полные требования к терминалу

**Что внутри:**
- Выполнение команд терминала (`handlers/`, `mcp/server/modules/Terminal.cjs`)
- Управление рабочими директориями (workspace) (`mcp/Workdir.cjs`, `mcp/Workdir.mjs`)
- История команд и сессий
- Модульная архитектура терминала (`mcp/server/modules/`)
- Поддержка различных ОС (Windows, Linux, macOS) (`mcp/CommandConverter.cjs`)
- Таймауты и фоновый режим

**Что вне:**
- Безопасность команд (в `security/`)
- Тестирование (в `testing/`)

**Планы миграции (будущее):**
- Требования для будущей пакетной архитектуры: `packages/*/docs/requirements/` (планируется)

### Security (`security/`)
Требования к системе безопасности - валидация команд, анализ безопасности, защита от опасных операций.

**Файлы:**
- `requirements-security.md` - требования безопасности

**Что внутри:**
- Анализ безопасности команд
- Валидация входных данных и путей
- Ограничения на опасные операции
- Логирование безопасности
- Система самопроверки безопасности

**Что вне:**
- Функциональность терминала (в `terminal/`)

### Testing (`testing/`)

**Файлы:**
- `requirements-testing.md` - требования к тестированию

**Что внутри:**

### Operations (`operations/`)
Операционные требования - развертывание, мониторинг, логирование, метрики.

**Файлы:**

**Что внутри:**
- Развертывание и конфигурация

**Планы миграции (будущее):**

## 🔄 Синхронизация требований

Все требования синхронизируются через роль **Requirements Sync Coordinator** (`.carior/roles/requirements-sync/`).

**Принципы:**
- Единственный источник истины - каждое требование описано ровно в одном файле
- Нет дублирования - информация не повторяется между файлами
- Четкие границы ответственности - каждый файл отвечает за свою область
- Статусы реализации - ✅ РЕАЛИЗОВАНО или ❌ ОТСУТСТВУЕТ (нет "опционально")
- **Текущая структура** - требования отражают реальную структуру кода (`mcp/`, `handlers/`, `lib/`)
- **Планы миграции** - требования для будущей пакетной архитектуры документированы отдельно

## 📝 Правила работы с требованиями

### При добавлении нового компонента:
1. Определить раздел (core/terminal/security/testing/operations/features)
2. Добавить описание в соответствующий `requirements-*.md`
3. Обновить `requirements-status-tracker.md` как ❌ ОТСУТСТВУЕТ
4. Добавить требования к тестам в `requirements-testing.md`

### При реализации компонента:
1. Отметить как ✅ РЕАЛИЗОВАНО в `requirements-status-tracker.md`
2. Обновить соответствующий `requirements-*.md`
3. Обновить статус тестов в `requirements-testing.md`

### При изменении требования:
1. Обновить соответствующий `requirements-*.md`
2. Проверить связанные файлы (по матрице синхронизации)
3. Обновить статусы в tracker файлах

## 🚨 Критические правила

1. **НЕ ДУБЛИРОВАТЬ** - каждое требование только в одном файле
2. **ВСЕГДА синхронизировать** - при изменении одного файла обновлять связанные
3. **ВСЕГДА проверять границы** - информация должна быть в правильном файле
4. **НЕТ ПОНЯТИЯ "ОПЦИОНАЛЬНО"** - компонент либо ✅ РЕАЛИЗОВАНО, либо ❌ ОТСУТСТВУЕТ
