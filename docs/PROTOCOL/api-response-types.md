# API Response Types

Standardized response types for API endpoints in the A2A protocol, providing consistent error handling and data structure across all services.

## ApiResponse<T>

Generic wrapper for all API responses, providing success status, data payload, and error information.

### Fields

#### success
- **Type**: `boolean`
- **Description**: Indicates whether the API call was successful
- **Usage**: Client checks this first to determine response handling
- **Service Responsibility**: Set by API endpoint based on operation outcome

#### data
- **Type**: `T` (optional)
- **Description**: The response payload when success is true
- **Usage**: Contains the actual API response data
- **Service Responsibility**: Populated by successful API operations

#### error
- **Type**: `ApiError` (optional)
- **Description**: Error details when success is false
- **Usage**: Provides structured error information for client handling
- **Service Responsibility**: Set by error handling middleware or failed operations

## ApiError

Structured error information for API failures.

### Fields

#### code
- **Type**: `string`
- **Description**: Machine-readable error code
- **Examples**: "VALIDATION_ERROR", "NOT_FOUND", "PERMISSION_DENIED", "INTERNAL_ERROR"
- **Usage**: Client logic can handle specific error types programmatically
- **Service Responsibility**: Set by error handling code or service logic

#### message
- **Type**: `string`
- **Description**: Human-readable error message
- **Examples**: "Invalid request parameters", "Resource not found", "Access denied"
- **Usage**: Displayed to users or logged for debugging
- **Service Responsibility**: Generated by error handlers or service logic

#### details
- **Type**: `Record<string, unknown>` (optional)
- **Description**: Additional error context and debugging information
- **Examples**: Field validation errors, stack traces, request IDs
- **Usage**: Detailed error analysis and debugging
- **Service Responsibility**: Populated by error handling middleware

## PaginatedResponse<T>

Response wrapper for paginated list endpoints.

### Fields

#### items
- **Type**: `T[]`
- **Description**: Array of items for the current page
- **Usage**: The actual data items being returned
- **Service Responsibility**: Sliced from full dataset based on pagination parameters

#### total
- **Type**: `number`
- **Description**: Total number of items across all pages
- **Usage**: Calculate total pages and provide progress information
- **Service Responsibility**: Counted from full dataset

#### page
- **Type**: `number`
- **Description**: Current page number (1-indexed)
- **Usage**: Track current position in pagination
- **Service Responsibility**: Calculated from request parameters

#### per_page
- **Type**: `number`
- **Description**: Number of items per page
- **Usage**: Consistent pagination behavior
- **Service Responsibility**: From request parameters or default configuration

## Usage Patterns

### Successful Response
```typescript
{
  success: true,
  data: {
    id: "123",
    name: "Example Resource",
    createdAt: "2024-01-01T00:00:00Z"
  }
}
```

### Error Response
```typescript
{
  success: false,
  error: {
    code: "VALIDATION_ERROR",
    message: "Invalid input parameters",
    details: {
      field: "email",
      reason: "Invalid email format",
      value: "invalid-email"
    }
  }
}
```

### Paginated Response
```typescript
{
  success: true,
  data: {
    items: [
      { id: "1", name: "Item 1" },
      { id: "2", name: "Item 2" }
    ],
    total: 25,
    page: 1,
    per_page: 10
  }
}
```

## Service Responsibilities

### API Controllers
- Set `success` based on operation outcome
- Populate `data` for successful operations
- Generate appropriate error responses

### Error Middleware
- Catch exceptions and convert to `ApiError` format
- Add appropriate error codes and messages
- Include relevant debugging details

### Pagination Services
- Handle page/per_page parameter validation
- Calculate correct slicing for `items`
- Provide accurate `total` counts
- Maintain consistent pagination behavior

## Error Code Standards

Common error codes used across the system:

- `VALIDATION_ERROR`: Input validation failures
- `NOT_FOUND`: Requested resource doesn't exist
- `PERMISSION_DENIED`: Authentication/authorization failures
- `RATE_LIMITED`: Too many requests
- `INTERNAL_ERROR`: Unexpected server errors
- `SERVICE_UNAVAILABLE`: External service failures
- `BAD_REQUEST`: Malformed request data

## Client Error Handling

Clients should:

1. Always check `success` first
2. Handle specific error codes programmatically
3. Display `message` to users for user-facing errors
4. Use `details` for debugging and logging
5. Implement retry logic for transient errors
6. Handle pagination parameters for list endpoints

## Security Considerations

- Error messages should not leak sensitive information
- Stack traces in `details` should be sanitized in production
- Error codes should be stable across versions
- Rate limiting errors should not provide timing information
