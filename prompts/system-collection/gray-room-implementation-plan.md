# Серый Room Implementation Plan

## 1. Цель
Сформировать управляемый уровень (серую комнату), который:
- принимает пакеты запросов, преобразует их в `sequence` очередь (текущий шаг + 3–5 look-ahead шагов),
- контролирует и отображает завершение шагов (`step_complete`), переключает режимы и пересчитывает прогноз последнего шага при уменьшении пачки,
- оставляет промты в роли описания подхода, а источник правды — очередь, чеклисты и подтверждение агента.

## 2. Основные компоненты
| Компонент | Что делает | Ссылка/файл |
|-----------|------------|------------|
| `sequence` queue | Хранит текущий шаг и будущие шаги, содержит цель, критерий завершения и связи на промты/файлы. | `gray-room-overview.md`, `sequence-control.md` |
| Step confirmation | Агенты возвращают `step_complete` → серую комнату переводят в режим следующего шага. | `sequence-control.md` |
| Look-ahead prediction | Когда активных задач меньше запланированных шагов, формируем прогноз последнего шага, фиксируем в log/checklist. | `sequence-control.md`, `system-sequence-guidance.md` |
| Prompt weave | `system/sequence.txt`, `mutation/step_prompts.txt`, `mutation/chain_examples.txt` лишь описывают подход и используются для составления шагов. | `system-collection/version-1-system`, `gray-room-overview.md` |

## 3. Этапы реализации
1. **Сбор требований для очереди** — определить поля шагов (id, title, state, goal, exit criteria, dependencies, step prompt reference). Документировать формат (например, JSON schema or markdown table) и где хранится (file, DB, plan doc).
2. **Контроль и переходы** — описать механизм, как `step_complete` переводит очередь в следующий шаг, как система удерживает flow при отсутствии подтверждения и что происходит при изменении порядка/приоритета.
3. **Планирование look-ahead** — прописать: если backlog < planned steps, обновить последний шаг/прогноз и добавить описание зависимостей/блокеров. Указать, кто пересчитывает (скрипт, оператор, AI assistant).
4. **Документировать и связать с промтами** — обновить/создать:
   - `system/sequence.txt` (шаблон pipeline, реальные шаги, статус).
   - `mutation/step_prompts.txt` (шаговое описание, input/prompt/output/explanation).
   - `mutation/chain_examples.txt` (цепочки и примеры переходов).
   - `system/ai_editor_instructions.txt` (роль AI-редактора, формат сообщения `step_complete`).
5. **Операционное сопровождение** — зафиксировать:
   - Как добавляются/удаляются шаги (через план/композиции, log).
   - Как серый room документирует полный поток (overview, sequence-control, guidance).
6. **Интеграция/тест** — проверка: при запуске новой пачки очередь наполняется, `step_complete` переключает шаги, прогноз последнего шага корректно обновляется при уменьшении пакета.

## 4. Риски и критерии готовности
- Риск: округление `step_complete` сигнала → implement guard, чтобы повторный `step_complete` без изменений не продвигал шаг.
- Критерий готовности: есть живой `sequence` log, подтверждение `step_complete`, документировано как look-ahead обновляется, и промты/планы ясно обозначают, что очередь — единственный источник правды.

## 5. Следующие шаги
1. Заполнить `gray-room-implementation-plan.md` сценариями (пример sequence queue JSON).
2. Обновить `system/sequence.txt` и `mutation` файлы согласно описанной логике.
3. Стандартизировать `step_complete` сообщения (формат, что включает: id, summary, next step).
4. Внедрить лог `prediction of final step` (новый файл или запись в plan) и убедиться, что при сокращении пачки он обновляется.
