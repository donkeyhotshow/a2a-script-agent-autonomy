# Plan: Bug Analysis and Fixes for monitor-and-process-tasks.js

## Summary
Analysis of `monitor-and-process-tasks.js` revealed several bugs that need fixing. The script processes task files from `prompts-to-agent-mode/` and sends them to the A2A Client API.

---

## Identified Bugs

### Bug 1: Router Choice Logic - Wrong Parameter Key
**Location**: Lines 227-240

**Issue**: When router choices are detected, the code sends `{ task: choiceId }`. According to `step-routes-router-flow.js:46-51`, when `hasChoices` is true, the body should use `result.choice` not `task`. The router flow maps `task` to `choice` only when previous step had choices, but this logic is fragile.

**Fix**: Change `{ task: choiceId }` to `{ result: { choice: choiceId } }`.

---

### Bug 2: Double Task Submission
**Location**: Lines 193-196

**Issue**: When session is created with `task` in body (`createSession` at line 86), the task is already in `context.task`. Sending it again via `sendNext` with `{ result: { message: taskDescription } }` may cause duplicate submission or confusion in the server state.

**Fix**: After `createSession` with `task` parameter, skip the initial `sendNext` with message. The server should already have the task from session creation.

---

### Bug 3: Task Extraction - Fallback Too Broad
**Location**: Lines 306-314

**Issue**: If no pattern matches ("Agent prompt" or "task:"), fallback returns `lines[0].trim()`. This often returns title/header, not the actual task.

**Fix**: Improve extraction to look for specific patterns like `## Agent prompt` section or require explicit task field.

---

### Bug 4: Poll Loop - Missing Promise Check
**Location**: Lines 220-226

**Issue**: Code checks `promiseId` from response but doesn't distinguish between server-side promise (async) and client-side state. The `describeAsyncResult` is called but its output isn't used to decide the next step.

**Fix**: Use the result from `describeAsyncResult` to determine if we should continue polling or handle the response differently.

---

### Bug 5: Hardbit State Logging - Incorrect Parameter
**Location**: Line 205-206, 234-238

**Issue**: `logHardBit({ ..., serverBusy: true })` - the function signature is `logHardBit({ phase, serverBusy = false, llmBusy = false, promiseId, detail = '' })`. Passing `serverBusy: true` when we know server is processing is correct, but at lines 205-206 we call it outside the polling context where serverBusy might not be accurate.

**Fix**: Ensure `serverBusy` flag accurately reflects the actual server state at call time.

---

### Bug 6: Session ID Not Used in Poll Response
**Location**: Lines 214-262

**Issue**: The polling loop uses `session.id` but the `pollAsync` endpoint returns data that may need session context re-attachment. No verification that the session still exists.

**Fix**: Add session existence check in poll loop or re-hydrate session state.

---

## Implementation Plan

1. **FIXED: Router choice** - Changed `sendNext(session.id, { task: choiceId })` to `sendNext(session.id, { result: { choice: choiceId } })` at line 228.

2. **FIXED: Double submission** - After successful `createSession` with `task` param, now sends task via `sendNext` with `{ task: taskDescription }` and falls back to `{ result: { message: taskDescription } }` if needed.

3. **FIXED: Task extraction** - Improved to look for content after `## Agent prompt` section before falling back to other patterns.

4. **FIXED: Poll loop** - Added proper handling of promise states: now checks `hasPromiseId && !isCompleted` to continue polling when promise exists but not completed.

5. **FIXED: Hardbit logging** - Removed incorrect `promiseId` parameter and ensured accurate state flags.

6. **PARTIAL: Session verification** - Added promise inspection to verify server-side state during polling.

## Testing Results

- Poll loop now properly handles pending promises
- Hardbit logging cleaned up
